# Спецификация модулей пайплайна

Основа — `tehnicheskoe_zadanie.md`. Девять модулей, порядок соответствует потоку данных. Для каждого: вход/выход, зависимости, какую развилку реализует, конфиг-параметры. Реализация — переносить логику из уже рабочих Colab-скриптов (`test_1_3_*`, `test_2_2_*`, `test_2_3_*`), не писать заново с нуля.

---

## 1. Ingestion / парсинг

**Вход:** сырые файлы датасета — `FinQA_{train,dev,test}.parquet`, `ConvFinQA_turn_0.parquet`, `TAT-DQA_{train,dev,test}.parquet`.

**Выход:** нормализованная запись документа:
```
DocumentRecord {
  context_id: str
  context: str          # текст + сериализованная таблица, как в исходном датасете
  source_dataset: str    # "FinQA" | "ConvFinQA" | "TAT-DQA"
  question: str
  answer: str
}
```

**Зависимости:** нет — первый модуль.

**Развилка:** нет отдельной, задаёт формат данных для всех следующих модулей.

**Конфиг:** путь к директории с сырыми файлами (`data/t2-ragbench/`).

---

## 2. Chunking / сериализация таблиц

**Вход:** `DocumentRecord` из модуля 1.

**Выход:** тот же `DocumentRecord` — без изменений структуры. Один документ = один чанк (страница отчёта, текст+таблица уже цельная единица — подтверждено фактическим успехом retrieval-тестов, отдельная сериализация не потребовалась).

**Зависимости:** модуль 1.

**Развилка:** 4 (сериализация таблиц) — не тестировалась отдельно, переиспользован формат датасета, признан достаточным.

**Конфиг:** нет.

**Действие при кодировании (отмечено четырьмя независимыми внешними ревью, не закрыто до сих пор):** буквальный формат таблицы внутри `context` (markdown / HTML / plain-text с разделителями / формат конкретно TAT-DQA) нигде не задокументирован построчно — только «как в датасете». Перед написанием модуля 1 — открыть по одному документу с таблицей из каждого источника (FinQA/ConvFinQA/TAT-DQA), зафиксировать реальный формат явным примером в этом разделе. Не архитектурный риск (формат уже показал себя рабочим в тестах недель 1-2), но пробел для воспроизводимости, который не должен уйти в код "по умолчанию как получится".

---

## 3. Embedding

**Вход:** список текстов (документы **или** запросы, `input_type` различает).

**Выход:**
```
EmbeddingVector { context_id or question_id: str, vector: float[1024] }
```

**Зависимости:** модуль 1 (для документов); для запросов — вызывается напрямую в момент retrieval.

**Развилка:** 6 (embedding-модель).

**Конфиг:** `model="voyage-4"`, `batch_size=32`, `input_type ∈ {"document", "query"}`.

**Guard на порядок вызовов (замечание внешнего ревью):** документация фиксирует «enrichment → embedding», но это не защищено кодом само по себе. Функция эмбеддинга документов должна принимать на вход уже собранный `full_indexed_content` (готовый после модуля 4), а не строить его сама из `raw_content` — так неправильный порядок вызовов (например, в отдельном тестовом скрипте) физически не сможет случайно заэмбеддить сырой текст вместо обогащённого.

---

## 4. Contextual enrichment (опционально, этап индексации)

**Вход:** `DocumentRecord.context` (полный текст документа, далее называется `raw_content`).

**Выход:** `contextual_summary: str` — короткая справка (1-2 предложения) от Claude Haiku 4.5. Хранится **отдельным полем**, не объединяется с текстом на этом шаге (объединение — в модуле 5, поле `full_indexed_content`). Раздельное хранение полезно для отладки и повторной генерации при смене промпта без пересчёта retrieval с нуля.

**Зависимости:** модуль 1. Выполняется до модуля 3 (эмбеддится уже `full_indexed_content`, если включено).

**Развилка:** 3 (contextual chunks).

**Конфиг:** `enrichment.enabled: bool` (default `true`), `model="claude-haiku-4.5"`, `temperature=0.0` (детерминизм для регрессионного анализа), prompt caching включён.

**Устойчивость:** retry с экспоненциальным backoff на вызовах Claude API (`tenacity`), checkpointing прогресса по документам (какие уже обогащены) во внешнее состояние — обработка 7318 документов не должна начинаться заново при сбое на середине.

---

## 5. Indexing (MongoDB Atlas)

**Вход:** `DocumentRecord` (с `raw_content` и, если модуль 4 включён, `contextual_summary`) + `EmbeddingVector` из модуля 3.

**Выход:** заполненная коллекция `rag_project.t2_ragbench_full` с полями:
```
{
  context_id: str
  raw_content: str              # исходный текст, не изменяется
  contextual_summary: str       # справка от Haiku, пусто если enrichment выключен
  full_indexed_content: str     # = contextual_summary + "\n\n" + raw_content (или = raw_content, если enrichment выключен) -- по этому полю идёт и поиск, и reranking, и это же передаётся в generation
  embedding_voyage: float[1024] # эмбеддинг full_indexed_content
}
```
и построенными индексами.

**Зависимости:** модули 1, 3, 4.

**Развилка:** 1 (выбор БД — MongoDB Atlas).

**Конфиг (константы, не хардкод в разных файлах):**
```
MONGODB_URI: str
DB_NAME = "rag_project"
COLLECTION_NAME = "t2_ragbench_full"
VECTOR_INDEX_NAME = "vector_index_full"
TEXT_INDEX_NAME = "text_index_full"
```
**Обязательная проверка при старте пайплайна:** тестовый запрос к обоим индексам, assert на непустой результат — до того, как пайплайн продолжит работу (защита от уже случавшегося тихого бага несовпадения имён).

**Устойчивость:** checkpointing (`is_indexed: true` на уровне документа) — при сбое на середине индексации всего корпуса возобновлять с необработанных документов, не с нуля.

---

## 6. Hybrid retrieval

**Вход:** текст вопроса пользователя.

**Выход:** список из `pool_size` кандидатов, отсортированных по `$rankFusion`-скору:
```
Candidate { context_id: str, full_indexed_content: str, score: float }
```

**Зависимости:** модуль 5 (индекс), модуль 3 (эмбеддинг запроса, вызывается здесь же).

**Развилка:** 1 (реализация retrieval) + базовый baseline для развилок 2 и 3.

**Конфиг:** `pool_size=50` (default, обоснование — п.6 ТЗ), веса `{vector: 0.5, text: 0.5}`.

**Чекпоинт:** Recall@5 = 0.808 на eval-выборке без reranker/enrichment.

**Проверка:** дедупликация по `_id` в `$rankFusion` подтверждена официальной документацией MongoDB ([manual/reference/operator/aggregation/rankfusion](https://www.mongodb.com/docs/manual/reference/operator/aggregation/rankfusion/)) — не требует отдельной логики в коде. Расхождение "chunk vs parent document" (когда у одного документа несколько чанков с разными `_id`) к нашей схеме не относится — по модулю 2 один документ = один чанк = один `context_id`. Assert на отсутствие дублей оставить как дешёвую подстраховку, не как обязательную дедупликацию.

---

## 7. Reranking (опционально)

**Вход:** вопрос + `pool_size` кандидатов из модуля 6, **полный `full_indexed_content` без обрезки**. Это единственная версия текста, что попала в индекс (уже включает `contextual_summary`, если enrichment включён) — reranker не получает отдельно raw и enriched варианты.

**Выход:** top-5 переранжированных кандидатов.

**Зависимости:** модуль 6.

**Развилка:** 2 (reranker + оптимальный размер пула).

**Конфиг:** `reranker.enabled: bool` (default `true`), `model="rerank-v4.0-pro"`, `pool_size=50`, `top_n=5`. **Явный запрет обрезки текста документа** — это должно быть проверяемым инвариантом в коде (assert, что переданный в API текст равен `full_indexed_content` целиком, не срезу), не просто комментарием.

**Чекпоинт:** Recall@5 = 0.944 (пул=50, без обрезки, n=900).

---

## 8. Generation

**Вход:** вопрос + top-5 контекстных документов (после reranking, если включён, иначе — top-5 из модуля 6).

**Выход:**
```
GeneratedAnswer { question_id: str, answer_text: str, raw_response: str }
```

**Зависимости:** модуль 7 (или 6, если reranker выключен).

**Развилка:** 9 (формат ответа — Direct, не PoT).

**Конфиг:** `model="claude-sonnet-5"`, `temperature=0.0` (детерминизм для регрессионного анализа), промпт явно требует формат, инвариантный к знаку и масштабу (проценты как число 0-100, не доля 0-1 — явно прописать в промпте, не полагаться на угадывание моделью).

**Чекпоинт:** точность 0.733 на 30 gold-context вопросах (сравнение через `is_close_v2`, см. модуль 9).

---

## 9. LLM Judge Evaluation (переименовано из «RAGAS evaluation» — не использует библиотеку RAGAS/её метрики, только кастомный judge + `is_close_v2`)

**Вход:** вопрос, `GeneratedAnswer`, retrieved context, gold-ответ.

**Выход:**
```
EvalResult { question_id: str, judge_scores: dict, deterministic_match: bool, judge_agrees: bool }
```

**Зависимости:** модуль 8.

**Развилка:** 7 (LLM-судья) + развилка 8 (критерий готово).

**Конфиг:** `judge_model="claude-sonnet-5"`, `temperature=0.0`, `deterministic_check.enabled=true` (функция `is_close_v2`, инвариантная к знаку/масштабу — использовать именно её, не наивное сравнение строк/чисел). **Точная логика `is_close_v2` (допуск, обработка None/валют/единиц) — см. ТЗ п.7, обязательна к переносу буквально из Colab-скрипта теста 2.4/2.5, не переписывать по памяти.**

**Кэширование:** ключ `hash(question + context + answer + judge_prompt_version)` — версия промпта судьи обязательна в ключе (см. ТЗ п.8, иначе смена промпта судьи тихо вернёт оценки по старому промпту). При повторном прогоне (например, менялась генерация только для части вопросов, п.10 ТЗ требует регрессионный анализ после каждого значимого изменения) — не пересуживать вопросы, где входные данные не изменились.

**Обязательный выход модуля для отчётности:** регрессионный отчёт (что было верно/стало неверно относительно предыдущего прогона) и финальная классификация оставшихся ошибок по паттернам — не только агрегированные метрики.

## Общие инженерные принципы (все модули с вызовами внешних API — 3, 4, 6, 7, 8, 9)

- Retry с экспоненциальным backoff (`tenacity`, `stop_after_attempt(5)`, `wait_random_exponential(min=1, max=60)`) — не временный `time.sleep()` вручную, как было оправдано в тестовых Colab-скриптах недель 1-2.
- Параллелизм — `concurrent.futures.ThreadPoolExecutor` для батчевых вызовов API. Без Celery/распределённых очередей — не оправдано для масштаба проекта.
- `temperature=0.0` на всех вызовах LLM (enrichment, generation, judge) — обязательное условие для воспроизводимого регрессионного анализа (п.10 ТЗ).
