# План подготовки к кодированию

Основа — `tehnicheskoe_zadanie.md`, `specifikatsiya_moduley.md`, `struktura_repozitoriya.md`. Порядок реализации — от простого и наиболее проверенного к сложному, с чекпоинтом на каждом шаге: если число не сходится с зафиксированным в ТЗ больше, чем объясняет шум выборки — это сигнал бага в реализации, останавливаться и разбираться, не идти дальше молча (правило документа из ТЗ, п.5).

**Важное уточнение к порядку (отличается от первого черновика плана недели 1-2):** финальная спецификация зафиксировала enrichment **до** embedding (модуль 4 выполняется до модуля 3 — эмбеддится уже `full_indexed_content`, не `raw_content`). Порядок шагов ниже это учитывает — enrichment интегрируется не отдельным довеском после reranking, а как часть шага 2, с `enrichment.enabled=false` на первом проходе.

**Второе важное уточнение — какие чекпоинты на каком масштабе корпуса измерены (не перепутать несовпадение с багом):**

| Чекпоинт | Значение | Корпус |
|---|---|---|
| Retrieval без reranker/enrichment | Recall@5 = 0.808 | полный, 7318 документов |
| Reranker (пул=50), без enrichment | Recall@5 = 0.944 | полный, 7318 документов |
| Enrichment без reranker | Recall@5 = 0.933 | **уменьшенный, 450 документов** |
| Enrichment + reranker вместе | Recall@5 = 0.980 | **уменьшенный, 450 документов** |

Два нижних числа — открытый риск ТЗ (п.5): не подтверждены на полном корпусе. Если на шаге 5 ниже (полный корпус, enrichment включён) результат не совпадёт с 0.933/0.980 — **это ожидаемо и не обязательно бага**, это ровно то, что должен измерить сквозной прогон недели 4. Не путать с шагами 3-4, где несовпадение с 0.808/0.944 (полный корпус, те же условия) — почти наверняка бага в реализации.

---

## Шаг 1 — Ingestion + Chunking

Модули 1-2. Нет внешних зависимостей, тестируется на структуре данных, не на метрике.

**Чекпоинт:** количество распарсенных документов = 7318, количество вопросов = 23088 (п.1 ТЗ). Явный assert на это число при первом полном проходе по датасету — расхождение сигнализирует ошибку парсинга одного из трёх источников (FinQA/ConvFinQA/TAT-DQA), не проблему дальше по пайплайну.

**До начала:** зафиксировать буквальный формат таблиц в `context` — открыть по одному документу с таблицей из каждого источника, записать пример в `specifikatsiya_moduley.md` (модуль 2, уже отмечено как явное действие по итогам внешнего ревью).

## Шаг 2 — Embedding + Indexing, `enrichment.enabled=false`

Модули 3-5 (enrichment на этом шаге тривиален — `contextual_summary=""`, `full_indexed_content=raw_content`, реальные вызовы Haiku не идут). Цель шага — проверить embedding+indexing независимо от enrichment, на более простом случае.

**Чекпоинт:** корпус проиндексирован — 7318 документов в `t2_ragbench_full`, оба индекса (`vector_index_full`, `text_index_full`) построены. **Обязательная startup-проверка** (ТЗ п.2): тестовый запрос к обоим индексам, assert на непустой результат — до перехода к шагу 3.

**Записать `run_config.json`** для этого прогона (`enrichment.enabled=false`) — точка отсчёта для последующего сравнения.

## Шаг 3 — Hybrid retrieval, `enrichment.enabled=false`, `reranker.enabled=false`

Модуль 6.

**Чекпоинт: Recall@5 = 0.808** на eval-выборке, полный корпус (ТЗ п.4). Известное число — если не сходится, баг в retrieval-модуле (веса `$rankFusion`, размер пула, эмбеддинг запроса), не идти дальше, пока не сойдётся.

## Шаг 4 — Reranking поверх retrieval, `enrichment.enabled=false`

Модуль 7.

**Чекпоинт: Recall@5 = 0.944**, пул=50, полный текст без обрезки (ТЗ п.6). Если результат заметно ниже — **первым делом проверить обрезку текста документа перед Cohere API** (дважды подтверждённая причина регресса в тестах недель 1-2) и совпадение размера пула, не пересматривать архитектуру.

**Записать `run_config.json`** для этого прогона.

## Шаг 5 — Contextual enrichment, `enrichment.enabled=true`

Модуль 4 включается по-настоящему (реальные вызовы Claude Haiku 4.5). Повторный проход по шагам 2-4 с `enrichment.enabled=true`: `full_indexed_content` теперь содержит `contextual_summary + raw_content`, эмбеддинги и индекс пересчитываются на этом тексте.

**Чекпоинт на полном корпусе:** ожидается число **в районе** 0.933 (enrichment без reranker) и **в районе** 0.980 (enrichment + reranker вместе) — но по таблице выше, оба этих числа измерены на уменьшенном корпусе (450 документов), не подтверждены на полном 7318. Заметное расхождение здесь **не автоматический признак бага** — записать фактический результат, сравнить статистически (paired bootstrap/McNemar, ТЗ п.9) с шагами 3-4 как baseline, задокументировать в ТЗ (закрывает открытый риск п.5) независимо от того, воспроизвелось число или нет.

**Записать `run_config.json`** для этого прогона (`enrichment.enabled=true`).

## Шаг 6 — Generation

Модуль 8.

**Чекпоинт: точность 0.733** на 30 gold-context вопросах (ТЗ п.7), сравнение через `is_close_v2` — юнит-тесты `is_close_v2` (`tests/test_is_close_v2.py`) должны быть написаны и пройдены **до** этого шага, не после: если функция сравнения содержит баг, чекпоинт 0.733 воспроизведётся неправильно и введёт в заблуждение на старте, не в конце.

## Шаг 7 — LLM Judge Evaluation, интеграция всего пайплайна

Модуль 9.

**Чекпоинт:** 93.3% согласия судьи с детерминированной проверкой на тех же 30 вопросах (ТЗ п.8). После этого — полный сквозной прогон на финальном eval-наборе (размер зафиксировать явно перед прогоном, не «весь датасет» без числа — см. открытый пробел из внешнего ревью про бюджет полного прогона), с обязательными этапами оценки из ТЗ п.10 (диагностика по типам, регрессионный анализ, ручной разбор 10-20 ошибок, стратификация по `source_dataset`).

**Это и есть тот самый сквозной прогон недели 4**, который должен подтвердить или опровергнуть открытый риск ТЗ п.5 (enrichment/enrichment+reranker на полном корпусе) — результат дописать в ТЗ по факту, не предполагать заранее.
