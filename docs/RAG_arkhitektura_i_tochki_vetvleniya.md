# Архитектура и точки ветвления — новый RAG-проект (FinQA/TAT-QA)

Дата: 2026-08-07 (редакция 3 — учтены реально доступные ресурсы: Claude API + MongoDB Atlas + Google Colab/Drive 30 ГБ; обновлены развилки 1, 6, 7 под фактический стек)
Статус: черновик для решения перед началом кодирования. Следующий документ по методологии — Техническое задание.

## Как читать этот документ

Ниже — не финальная архитектура, а список развилок, по каждой из которых нужно решение до старта кодирования. Для каждой развилки: аргументы за и против (с источниками), предлагаемый способ дешёво проверить гипотезу за часы, а не недели, и предварительная рекомендация — обратимая, если тест её не подтвердит.

Порядок важен и не сводится к простой последовательности «одна развилка за другой». Датасет (развилка 5) определяет, на чём вообще проверяются все остальные гипотезы — его нужно закрыть первым. Reranker и contextual chunks (развилки 2 и 3) не гарантированно складываются аддитивно — комбинацию нужно проверять отдельно, а не предполагать, что раз обе техники полезны по отдельности, вместе будет ещё лучше (урок из finetuning-методологии: в Text-to-SQL проекте постобработка + few-shot иногда давали регрессию именно в паре). Итоговый порядок действий — в конце документа.

### Обязательные этапы оценки — не только метрика

Перенесено из методологии fine-tuning-проектов (Text-to-SQL), принцип общий, не специфичный для дообучения:

- **Диагностика перед починкой.** Прежде чем добавлять технику (reranker, contextual chunks) — реально разделить текущие ошибки по типам (retrieval miss / неверная таблица-источник / верный контекст, но генерация ошиблась) на выборке реальных примеров. Не гадать, какая техника нужна.
- **Регрессионный анализ после каждого изменения.** Не только агрегированный Recall@5/RAGAS-скор — сравнение по конкретным запросам: что было верно и стало неверно, что было неверно и стало верно.
- **Финальный ручной разбор ошибок.** Перед тем как считать этап законченным — просмотреть 10-20 оставшихся ошибок вручную, классифицировать по паттернам (в Text-to-SQL так нашли, что 91% оставшихся ошибок были логическими и концентрировались на одной схеме — конкретный, а не общий вывод).

## Уточнение статуса референсов (обновлено)

**sec-mdna-rag** (github.com/AndyYTHsiao/sec-mdna-rag) — важное уточнение по итогам обсуждения: это репозиторий одного автора, 0 звёзд, не проверенный сообществом. Ablation-цифры внутри него (+41.67% Recall@1 от metadata-фильтрации) — результат одного эксперимента одного автора, не многократно воспроизведённый факт. Использовать как источник идей и отправную точку архитектуры (metadata-схема, структура пайплайна), не как проверенный стандарт.

**Найдены значительно более сильные источники именно для нашего домена** (текст+таблицы, финансы) — это меняет вес доказательств в развилках 2, 3 и 5 ниже:

- **T²-RAGBench** (Strich et al., Uni Hamburg, HCDS group, 2026) — академический benchmark, который решает ровно нашу развилку 5 (объединение FinQA/TAT-QA), причём лучше, чем мы планировали: объединяет FinQA + ConvFinQA + TAT-DQA (23 088 вопросов, 7 318 документов, текст+таблицы), с ключевым усовершенствованием — переформулировкой вопросов через LLM в context-independent форму (с указанием компании/сектора/года), поскольку у исходных датасетов вопросы в основном oracle-context (>90% вопросов originally были однозначны только при уже данном правильном контексте — то есть плохо тестируют реальный retrieval). Датасет опубликован на HuggingFace (`G4KMU/t2-ragbench`).
- **«From BM25 to Corrective RAG» (Akarsu, Karaman, Mierbach, апрель 2026)** — систематический бенчмарк 10 стратегий retrieval (sparse, dense, hybrid fusion, cross-encoder reranking, query expansion, index augmentation, adaptive retrieval) именно на T²-RAGBench, то есть на текст+таблица финансовых документах. Это прямая, а не по аналогии, эмпирика для развилок 2 и 3 — см. ниже.

Обе работы — препринты 2026 года, не многолетне воспроизведённый консенсус, но методологически они прямо в нашем домене (финансы, текст+таблицы), в отличие от LegalBench-RAG (юридический домен) и Anthropic-цифр (общие датасеты) — по принципу «не путать применимые и неприменимые референсы» им стоит отдавать больше веса, но не заменять ими собственную дешёвую проверку.

## Развилка 1. Векторная БД: LanceDB vs Qdrant vs MongoDB Atlas

**Вопрос:** на чём строить hybrid search (BM25 + dense + RRF) — embedded LanceDB, Qdrant (сервер, обычно через Docker), или MongoDB Atlas, доступ к которому уже есть.

**Что показало исследование референсных репозиториев:** sec-mdna-rag использует FAISS — прямого прецедента по этой развилке в нём нет. pablograba/financial-10k-agentic-rag и datapizza-labs/contextual-retrieval-experiments оба используют Qdrant осознанно — нативный hybrid (dense+sparse BM25), встроенный reranking-слот, RRF «из коробки», зрелый Python-клиент, metadata-фильтрация на больших объёмах.

LanceDB: embedded, in-process формат на базе Lance — без сервера, без портов, без инфраструктуры; vector search, full-text search и SQL-style запросы бок о бок. Ближе к «одна библиотека, pip install».

**Третий, ранее не рассмотренный кандидат — MongoDB Atlas, доступ к которому уже есть.** Свободный тариф M0 поддерживает Atlas Vector Search и нативный hybrid search через агрегационный этап `$rankFusion`, который реализует Reciprocal Rank Fusion «из коробки» — объединяет полнотекстовый (BM25-подобный Atlas Search) и векторный поиск в одном запросе (требует MongoDB v8.1+). M0 бесплатен без ограничения по времени, но с жёстким лимитом 512 МБ хранилища — для корпуса FinQA/TAT-QA/T²-RAGBench (тысячи чанков) должно хватить, но параллельно держать несколько экспериментальных вариантов корпуса (с contextual chunks и без) в одном кластере не стоит. Ключевое отличие от Qdrant/LanceDB не в качестве ретрива, а в нулевой предельной стоимости настройки — аккаунт уже есть, доп. инфраструктуры разворачивать не нужно.

**Дополнение из «From BM25 to Corrective RAG»:** на финансовых текст+таблица документах BM25 обгоняет современный dense retrieval («challenging the common assumption that semantic search universally dominates»). Это не аргумент за конкретную БД, но важный входной параметр: движок должен позволять гибко настраивать вес BM25-компонента в RRF/fusion, а не считать dense-часть доминирующей по умолчанию. Все три кандидата это умеют (Atlas — через `$rankFusion`).

**Аргумент за LanceDB:** ниже порог для рецензента (работодателя) — склонировал, `pip install`, запустил, без Docker.

**Аргумент за Qdrant:** фактический стандарт в обоих production-ориентированных референсах домена; встроенный reranking снимает часть кода для развилки 2.

**Аргумент за MongoDB Atlas:** уже есть доступ и настроенный аккаунт — ноль дополнительной инфраструктуры; нативный `$rankFusion` закрывает ровно то же самое, что Qdrant делает через RRF; хорошо ложится на Colab (эфемерные сессии не проблема — кластер живёт отдельно от Colab runtime, в отличие от Qdrant-в-Docker, который пришлось бы поднимать заново в каждой сессии).

**Дешёвый способ проверить:** пол дня. Минимальный hybrid-пайплайн на ~50-80 чанках во всех трёх (Atlas — на уже существующем кластере, LanceDB и Qdrant — как раньше). Замерить трение (время от старта до первого ответа, объём кода, нужен ли внешний аккаунт/Docker), не качество ретрива — на 50 чанках разница в скоре не показательна.

**Предварительная рекомендация (обновлено):** MongoDB Atlas — решающий фактор не архитектурное превосходство, а нулевая предельная стоимость (аккаунт уже есть, `$rankFusion` закрывает hybrid+RRF нативно) и совместимость с Colab-сессиями без Docker. Qdrant остаётся запасным вариантом, если тест покажет проблему с лимитом 512 МБ или с preview-статусом `$rankFusion`. Как и раньше — прятать доступ к БД за retriever-абстракцией, чтобы смена backend не требовала переписывать пайплайн.

## Развилка 2. Нужен ли reranker — и не навредит ли он в финансовом домене

**Вопрос:** добавлять ли cross-encoder reranking поверх hybrid+RRF, и если да — какой.

**Обновлено новым источником.** Раньше здесь была одна настораживающая точка данных из смежного домена: LegalBench-RAG обнаружил, что generic reranker (Cohere) ухудшал retrieval на юридических текстах из-за domain-жаргона. Это по-прежнему честное предупреждение против слепой веры «reranker всегда помогает».

Но «From BM25 to Corrective RAG» даёт прямую, не по аналогии, эмпирику **именно в нашем домене**: двухступенчатый pipeline hybrid retrieval + neural reranking даёт Recall@5 = 0.816 и MRR@3 = 0.605, превосходя все одноступенчатые методы с большим отрывом — на 23 088 запросах над 7 318 финансовыми текст+таблица документами (T²-RAGBench). Это прямо противоположно находке LegalBench-RAG — то есть эффект reranker явно доменно-зависим, а не универсален ни в одну, ни в другую сторону, что подтверждает исходную позицию документа: не решать заранее.

**Дешёвый способ проверить:** на выборке ~30-50 запросов (подмножество T²-RAGBench/FinQA/TAT-QA + собственные вопросы) прогнать hybrid-ретрив с локальным бесплатным reranker'ом (FlashRank или bge-reranker, без API-затрат, без GPU) и без него; сравнить Recall@5/NDCG@5, при готовом RAGAS-слое — Context Precision. Часы, не дни.

**Предварительная рекомендация:** ожидание сместилось в сторону «вероятно поможет» (в отличие от нейтральной позиции в редакции 1) — «From BM25 to Corrective RAG» прямо в нашем домене, с большим отрывом. Но это один препринт, не консенсус — решать по собственной абляции, не по одной цифре чужой работы, и держать reranker переключаемым.

**Итог развилки (закрыто 2026-08-09, полная хронология в `poshagovyi_plan_vypolneniya.md`): reranker используется, Cohere Rerank v4.0 Pro.** Два отдельных, изначально независимо найденных вывода:

*Длина документа (обрезка контекста) — решающий фактор.* Первые два раунда теста (FlashRank, затем Cohere/bge с обрезкой документов до 2000 символов перед подачей в reranker) дали ложноотрицательный результат — reranker выглядел вредным (Recall@5 падал с 0.808 до 0.608-0.764). Причина: 93.2% целевых документов длиннее 2000 символов (медиана 4263, максимум 14782 симв.) — обрезка отсекала больше половины релевантного текста в среднем. После снятия обрезки (полный текст документа в reranker) тот же Cohere Rerank v4.0 Pro дал Recall@5 = 0.868 (пул=10) — не регресс, а прирост +6.0 п.п. Вывод: **не обрезать документы перед reranking**, даже если это увеличивает объём данных, передаваемых в API.

*Размер кандидатного пула — оптимум найден эмпирически, не по прецеденту.* Протестированы пул=10, 50 и 100 (без обрезки текста, полный корпус 7318 документов, финально — на выборке n=900 с точным парным McNemar-тестом): пул=10 → Recall@5=0.890, пул=50 → 0.944 (значимо лучше пула=10, +5.44 п.п., p<0.0001), пул=100 → 0.941 (не отличается от пула=50, p=0.58, численно даже чуть хуже). **Оптимальный размер пула — 50**: дальнейшее расширение не даёт прироста на нашем корпусе (в отличие от контрадикторной статьи Akarsu et al., где 50→100 давало ещё +6-7 п.п. — объясняется более слабым baseline retrieval в их пайплайне, у них было больше "доступного потенциала" для reranker'а на любом размере пула).

Финальная конфигурация: hybrid `$rankFusion` (BM25 + Voyage-4, top-50) → Cohere Rerank v4.0 Pro (полный текст без обрезки, top-50 → top-5) → **Recall@5 = 0.944** (на выборке n=900, полный корпус).

## Развилка 3. Contextual chunks — да/нет

**Вопрос:** обогащать ли каждый чанк LLM-сгенерированным контекстом перед эмбеддингом.

**Обновлено новым источником.** Раньше единственная количественная опора была на цифры Anthropic (35% / 49% / 67% снижения failed retrievals), измеренные на их собственных generic-эвалах (код, документация), не на финансах — переносимость была правдоподобна, но не доказана.

«From BM25 to Corrective RAG» даёт прямое подтверждение в нашем домене: query expansion (HyDE, multi-query) и adaptive retrieval дают ограниченную пользу для точных численных запросов, **а contextual retrieval даёт стабильный прирост** («consistent gains») — именно на T²-RAGBench, то есть на финансовых текст+таблица документах, где вопросы часто требуют точных чисел. Это самое прямое доказательство для этой развилки из всех четырёх, что делает предварительную рекомендацию менее «занимать нейтральную позицию», чем раньше.

**Прецедент по коду:** datapizza-labs/contextual-retrieval-experiments — рабочий пайплайн для теста (флаг `--skip-contextual-retrieval`, Qdrant, character-span coverage). Требует адаптации под финансовый промпт-шаблон (как у них — под D&D).

**Стоимость:** один LLM-вызов на чанк на этапе ингестии (полный документ + чанк в промпте, с prompt caching), внешняя зависимость от LLM API на этапе построения индекса, лишняя точка отказа для портфолио-демо.

**Дешёвый способ проверить:** ~200 чанков из 4-5 документов, ingestion с обогащением и без, 20-30 QA-пар, сравнить Recall@5/NDCG@5 и посчитать реальную стоимость на выборке, экстраполировать на весь корпус. Дополнительно — важно проверить **не изолированно**, а поверх уже включённого (если подтвердится) reranker'а из развилки 2, поскольку аддитивность эффектов не гарантирована (см. «Как читать этот документ» выше).

**Предварительная рекомендация:** сместилась в сторону «вероятно включать», при условии приемлемой стоимости индексации на нашем объёме данных — «consistent gains» именно на численных финансовых запросах прямо релевантно FinQA. Финальное решение — по собственному тесту, не по цитате.

## Развилка 4. Сериализация таблиц FinQA/TAT-QA

**Вопрос:** как кодировать таблицу в чанк для эмбеддинга — построчная сериализация, markdown-таблица целиком, текст+таблица вместе или раздельно.

Ни один из трёх GitHub-референсов не решает эту проблему за нас (MD&A-проза, D&D SRD, или XBRL-факты, извлечённые отдельно от нарратива, а не через chunking таблицы как текста). T²-RAGBench и FinQA/ConvFinQA используют FinTabNet как источник PDF — при адаптации T²-RAGBench (развилка 5) стоит явно посмотреть, как они сериализуют таблицы в своём released коде/датасете, прежде чем изобретать свой вариант с нуля — это может закрыть развилку почти бесплатно.

**Дешёвый способ проверить:** 10-15 вопросов, где ответ явно требует таблицы, закодировать 2-3 способами, сравнить, какой чаще попадает в top-5.

**Предварительная рекомендация:** сначала проверить, что уже сделано в T²-RAGBench/released коде (может отпасть как отдельная развилка), и только если это не подходит — прогонять собственный тест.

## Развилка 5. Объединение FinQA и TAT-QA (в значительной мере уже решено находкой)

**Вопрос был:** использовать оба датасета параллельно с раздельной оценкой, вручную объединить в единую схему, или выбрать один для первой версии — ни один из 4 опрошенных ранее ИИ явно не предлагал схему объединения.

**Находка меняет постановку вопроса.** Существует прямое академическое прецедентное решение — **T²-RAGBench**, которое объединяет FinQA + ConvFinQA + TAT-DQA (родственный TAT-QA документ-уровневый вариант) в единый benchmark на 23 088 вопросов/7 318 документов, причём решает попутно и более фундаментальную проблему: у исходных FinQA/TAT-QA вопросы в основном oracle-context (правильный контекст уже дан условиями задачи, retrieval по сути не тестируется по-настоящему) — T²-RAGBench переформулировал вопросы через LLM (Llama 3.3-70B) в context-independent форму (>80% context-independence против <10% у оригиналов), что критично именно для RAG-оценки, а не для QA-оценки в узком смысле.

**Практический вывод:** вместо ручного объединения FinQA+TAT-QA с нуля — рассмотреть прямое использование или адаптацию датасета `G4KMU/t2-ragbench` (HuggingFace). Это не только снимает работу по унификации схемы, но и даёт готовую эмпирику для сравнения (развилки 2 и 3 выше уже используют её цифры).

**Дешёвый способ проверить:** скачать `G4KMU/t2-ragbench`, изучить схему и лицензию, прочитать 20-30 вопросов вручную на соответствие ожиданиям проекта (реальные ли это осмысленные вопросы, подходит ли объём для 3-5-недельного MVP или нужно подмножество), сравнить с ручным объединением по трудозатратам. Решение — использовать целиком, взять подмножество, или (если лицензия/качество не подойдёт) вернуться к ручному объединению — тогда взять методологию T²-RAGBench (context-independent переформулировка вопросов) как образец, а не строить с нуля.

**Предварительная рекомендация:** начать с адаптации T²-RAGBench, а не с ручного объединения — это резко снижает объём работы именно там, где ни один из ранее опрошенных ИИ не дал ответа.

## Развилка 6. Модель эмбеддингов для dense-retrieval

**Вопрос:** локальная бесплатная модель (self-hosted, воспроизводимо и без API-ключа) или платный API (выше качество по общим MTEB-бенчмаркам, но зависимость от ключа и сети для того, кто клонирует репозиторий).

**Что показало исследование:** по 2026 MTEB-рейтингам лидируют BGE-M3 и Qwen3-Embedding среди открытых моделей — оба самостоятельно размещаемые (self-hosted), бесплатные, многоязычные. Платные API (Cohere embed-v4 — 65.2 MTEB, OpenAI text-3-large — 64.6) обгоняют BGE-M3 (63.0) на несколько пунктов, но не принципиально — разница не того порядка, что определяет успех/провал проекта. Важная оговорка из тех же источников: для по-настоящему domain-specific задач (финансы, юриспруденция, медицина) рекомендуется fine-tuned BGE-M3 или коммерческие domain-specific предложения — «из коробки» общая модель не оптимальна ни для какого домена, наш в том числе.

**Дополнение из «From BM25 to Corrective RAG»:** раз BM25 обгоняет dense retrieval на финансовых документах, выбор конкретной embedding-модели, вероятно, менее критичен для итогового качества, чем вес BM25 в fusion — это снижает цену ошибки в этой развилке.

**Дешёвый способ проверить:** прогнать hybrid retrieval на тестовой подвыборке с BGE-M3 (локально, бесплатно) и с одним платным API, сравнить Recall@5 delta и реальную стоимость индексации всего корпуса при платном варианте.

**Обновлено под фактический стек — Voyage AI.** Voyage AI — официально рекомендованный партнёр Anthropic по эмбеддингам для Claude (у Anthropic нет собственного embeddings-эндпоинта), и с 2025 года Voyage AI принадлежит MongoDB — то есть при уже выбранной связке Claude + MongoDB Atlas (развилка 1) это не третий независимый сервис, а естественно сочетающийся стек. Цена (voyage-3.5) — $0.06 за миллион токенов: для корпуса в несколько тысяч чанков эмбеддинг всего корпуса стоит доллары, не десятки долларов.

**Предварительная рекомендация (обновлено):** Voyage AI как практический выбор по умолчанию — нулевое трение (тот же экосистемный периметр, что Claude/Atlas), низкая цена, официально рекомендован для связки с Claude. BGE-M3 остаётся дешёвым способом проверки — прогнать оба на подвыборке и сравнить Recall@5, прежде чем фиксировать выбор в ТЗ, а не просто принять более удобный вариант без проверки.

## Развилка 7. LLM-роли: генерация ответа и RAGAS-судья

**Вопрос:** это две отдельные роли, требующие отдельных решений — ни разу явно не обсуждались за 4 раунда с разными ИИ.

**LLM, генерирующий финальный ответ по retrieved-контексту.** Требования: доступность API, приемлемая стоимость демонстрации для рецензента, качество генерации по финансовым числам (галлюцинации на цифрах — известная слабость LLM в этой роли).

**LLM-судья для RAGAS.** Может быть той же моделью или другой. Практика: RAGAS поддерживает GPT-4o-mini как judge через `llm_factory` — дёшево ($0.15/M input, $0.60/M output), для коротких rubric-оценок экономически оправдан. Альтернатива — Claude с prompt caching, если rubric длинный и переиспользуется на многих примерах (кэшированная часть на 90% дешевле, может почти вдвое снизить общую стоимость оценки). Важно не смешивать модель-генератор и модель-судью без рефлексии — иначе есть риск, что судья систематически завышает оценку «своих» же ответов (self-preference bias, известная проблема LLM-as-judge).

**Дешёвый способ проверить:** прогнать оценку 20-30 примеров с двумя разными judge-моделями (например GPT-4o-mini и Claude), сравнить расхождение в оценках — если сильно расходятся, зафиксировать, какая ближе к ручной проверке человеком на этой малой выборке.

**Обновлено под фактический стек.** Генератор — Claude (уже есть ключ, Sonnet для качества или Haiku для дешевизны — Haiku 4.5: $1/$5 за млн токенов). Для судьи есть два пути: (а) тоже Claude (Haiku, отдельный от Sonnet-генератора) — дешевле и без нового ключа, но self-preference risk снижается не полностью, поскольку это по-прежнему одно семейство моделей одного вендора; (б) отдельный ключ (например GPT-4o-mini) — методологически чище, требует докупки. Per принцип «закупать ресурсы по мере необходимости, работа должна быть выполнена корректно» — если дешёвый тест (п. ниже) покажет, что Claude-as-judge систематически завышает оценку Claude-генерации, это станет конкретным основанием докупить второй ключ, а не гипотетическим риском.

**Предварительная рекомендация (обновлено):** начать с Claude для обеих ролей (Haiku-судья / Sonnet или Haiku-генератор — сравнить дешёвым тестом), явно прогнать сравнение с человеческой оценкой на 20-30 примерах для проверки на завышение, и решить по результату — докупать ли независимого судью. Prompt caching (кэш даёт 90% скидку на повторный контекст) особенно пригодится для contextual chunks (развилка 3) и снизит стоимость RAGAS-оценки при переиспользуемом rubric.

## Развилка 8. Числовой критерий «готово»

**Вопрос:** фиксированный порог RAGAS-метрик (например Faithfulness > 0.8) или просто честная задокументированная таблица без жёсткого порога.

**Что показало исследование:** универсального общепринятого порога нет. Встречается ориентир «Faithfulness выше 0.9 — output считается grounded», но реальные прикладные системы в специализированных доменах часто показывают заметно ниже (например, специализированная медицинская RAG-система — Faithfulness 0.70, Context Precision 0.59) и это не считается провалом, если соответствует характеру домена. Более практичная рекомендация из источников — не абсолютный порог, а relative к собственному baseline: посчитать метрики на первой рабочей версии, установить порог как ~95% от этого значения, и любое последующее падение ниже него на новых изменениях трактовать как регресс.

**Предварительная рекомендация:** не заявлять фиксированный абсолютный порог как критерий «успеха проекта» — использовать baseline-relative подход для внутреннего контроля регрессий по ходу разработки, а в README публиковать честные абсолютные цифры без утверждений о превышении произвольно выбранной планки. Соответствует исходному принципу «честная таблица метрик, не гонка за максимумом».

## Итоговый порядок действий (приоритет и стоп-условия)

1. **Закрыть развилку 5 (датасет)** — изучить и, вероятно, адаптировать T²-RAGBench. Это основа для всех последующих тестов; без неё дешёвые тесты остальных развилок не на чем ставить.
2. **Построить hybrid-baseline** на выбранной БД (развилка 1) с выбранной embedding-моделью (развилка 6) поверх датасета из шага 1.
3. **Проверить reranker (развилка 2)** на этом baseline. Если прирост существенный — включить и зафиксировать.
4. **Проверить contextual chunks (развилка 3) в двух режимах**: отдельно от reranker и поверх уже включённого reranker (если тот прошёл шаг 3) — чтобы не предполагать аддитивность, а измерить её. Если прирост в комбинации не оправдывает стоимость индексации — не включать, зафиксировать это как осознанное решение, не как недоделку.
5. **Развилку 4 (сериализация таблиц)** проверять только если T²-RAGBench не даёт готового решения — иначе позаимствовать их подход.
6. **Развилку 7 (LLM-роли)** закрыть параллельно с шагами 2-4 — не блокирует retrieval-эксперименты, но должна быть зафиксирована до перехода к ТЗ, поскольку RAGAS-оценка (шаги 3-4) уже требует judge-модели.
7. **Развилку 8 (критерий готово)** — это не эксперимент, а методологическое решение, принять сразу (baseline-relative, без фиксированного абсолютного порога) и использовать как гейт для регрессий на шагах 3-4.
8. Обязательные этапы оценки (диагностика по типам ошибок, регрессионный анализ по примерам, финальный ручной разбор 10-20 ошибок) — применять на каждом из шагов 3-4, не только в конце.
9. Зафиксировать все решения в Техническом задании со ссылкой на результат теста, не на интуицию, и перейти к следующему документу.
