## 1. Датасет и корпус

- **Источник:** T²-RAGBench = FinQA + ConvFinQA + TAT-DQA, объединены по методологии готового прецедента ([huggingface.co/datasets/G4KMU/t2-ragbench](https://huggingface.co/datasets/G4KMU/t2-ragbench), [paper](https://www.inf.uni-hamburg.de/en/inst/ab/lt/publications/2026-strich-t2ragbench.pdf)).
- **Масштаб:** 7318 документов (текст+таблица), 23088 вопросов.
- **Почему этот датасет:** признанный сложный тестовый случай для RAG — точные числовые ответы, высокая цена ошибки, смешанный текст+таблица формат. Обоснование ниши для портфолио — сложность датасета, не отраслевая статистика Upwork (см. `itogovyi_vyvod_proekt.md`).

## 2. Хранилище

- **MongoDB Atlas, тариф M0** (бесплатный, лимит 512 МБ и 3 search-индекса на инстанс — учитывать при создании новых коллекций для тестов).
- **Коллекция:** `rag_project.t2_ragbench_full`.
- **Имена индексов (константа, не хардкодить в разных местах кода):**
  - `vector_index_full` — векторный индекс, поле `embedding_voyage`
  - `text_index_full` — полнотекстовый индекс, поле `full_indexed_content` (исправлено 2026-08-09 — по итогам ревью, старое значение `context` было устаревшим: это имя поля из ранней версии схемы модуля 1/Ingestion, финальная схема индексации — модуль 5, поле `full_indexed_content`)

  Несовпадение этих имён с чем-либо ещё в коде уже один раз вызвало тихий баг: `$vectorSearch`/`$search` в MongoDB не бросает ошибку на несуществующее имя индекса, просто возвращает пустой результат — из-за этого баг легко спутать с "reranker всё сломал". Имена должны быть в конфиге, проверяться при старте пайплайна (явный assert на непустой результат тестового запроса), не потеряться повторно.

**Поправка на множественные сравнения (Bonferroni/FDR) не применяется** — по той же логике, что уже зафиксирована в п.9 этого документа: три сравнения (по одному на source_dataset) отвечают на три отдельные заранее спланированные архитектурные развилки ("нужен ли отдельный embedding для этого источника"), не батарея post-hoc гипотез на одних данных. Вопрос, применять ли здесь строгую поправку по традиции closed testing/gatekeeping, не решён однозначно в самой статистической литературе: за обязательность поправки в подобных случаях — традиция closed testing (Marcus/Peritz/Gabriel 1976, Westfall & Young 1993); против — Rothman 1990, Saville 1990, которые считают поправку неуместной именно для заранее спланированных, содержательно независимых гипотез. Политика проекта (п.9, зафиксирована заранее, независимо от этого конкретного случая) разрешает вопрос в пользу второй позиции — "без поправки для заранее спланированных отдельных гипотез".

### Решение (retrieval-уровень)

Per-dataset embedding routing: **voyage-finance-2 только для TAT-DQA** (`config/config.yaml`, `embedding.routing.routed_sources: ["TAT-DQA"]`). ConvFinQA и FinQA остаются на voyage-4 — их Δ отрицательны (ConvFinQA значимо, FinQA номинально), переключать их не оправдано.

Реализация: `pipeline/embedding.py` (`resolve_embedding_model()`), `pipeline/indexing.py` (`source_dataset` хранится на документе), `pipeline/retrieval.py` (pre-filter по `source_dataset` в `$vectorSearch`/`$search`), `config/config_schema.py` (`EmbeddingRoutingConfig`). Миграция уже проиндексированного корпуса — `scripts/migrate_embedding_routing.py` (backfill `source_dataset`, копирование уже посчитанных `embedding_finance2` → `embedding_voyage` для TAT-DQA, без новых API-вызовов). Обновление Atlas Search индексов (добавление `source_dataset` как filter-поля) — `scripts/update_atlas_search_indexes.py`, программно через pymongo driver-native search-index management, без ручного UI.

**Известное ограничение, не закрытое:** в гипотетическом production-сценарии (не eval, где `source_dataset` вопроса заранее известен из датасета) потребовалась бы классификация источника вопроса на этапе запроса — не реализовано, вне рамок этого портфолио-проекта, зафиксировано как ограничение архитектуры.

### Баг в первой реализации (найден и исправлен 2026-08-15)

Первый реальный прогон `python -m pipeline.cli eval` под routing на 250 вопросах показал неожиданную регрессию accuracy на ConvFinQA (−5.4 п.п. judge, 0.865→0.811) и FinQA (−1.1 п.п.) — источниках, чья embedding-модель routing не должен был затрагивать вообще.

**Причина:** `cmd_eval()` передавал `source_dataset=item["source_dataset"]` в `retrieve()` безусловно для каждого вопроса, ограничивая пул кандидатов только собственным источником даже для НЕ-routed вопросов. Это не то, что измерялось retrieval-A/B тестом выше (там сравнивался только эффект смены embedding-модели на полном, неограниченном пуле) — непреднамеренный побочный эффект реализации, а не архитектурное решение.

**Фикс:** `pipeline/retrieval.py` — новый параметр `exclude_source_datasets` (взаимоисключающий с `source_dataset`), использует Atlas `$nin`/`compound.mustNot`+`in`. `pipeline/cli.py` `cmd_eval()` теперь передаёт `source_dataset=` только для routed-вопроса (TAT-DQA), `exclude_source_datasets=<routed_sources>` для остальных — восстанавливая исходное поведение (полный пул по всем не-routed источникам) для ConvFinQA/FinQA, но по-прежнему исключая TAT-DQA (несовместимое embedding-пространство).

Sandbox-регрессия: 83/83 теста (полный `tests/`, включая 5 новых, различающих `$eq`-режим "только свой источник" и `$nin`-режим "исключить routed источники" — именно это различие пропустили предыдущие smoke-тесты из-за слишком маленького синтетического корпуса).

### Power analysis: сколько вопросов нужно для окончательного end-to-end ответа

Наблюдаемый на n=123 (TAT-DQA) end-to-end результат (2 вопроса стали правильными, 2 — неправильными, net 0, p=1.0) статистически не отличим от нуля — но это не значит, что эффекта нет: при таком n мощность теста крайне мала. Посчитано явно, не на глаз:

**Наблюдаемая доля discordant-пар** (вопросы, где baseline и routing дали разный вердикт правильности) на пилоте: `p_disc = 4/123 ≈ 0.0325`.

**Целевой эффект для обнаружения:** Δ = 0.02 (по аналогии с retrieval-level приростом +1.9 п.п.), то есть гипотетический сдвиг accuracy с 0.78 до 0.80.

Раскладываем `p_disc` на два direction-specific discordant-показателя через систему уравнений (p01 — доля "стало правильно", p10 — доля "стало неправильно", p01−p10=Δ, p01+p10=p_disc):

```
p01 = (p_disc + Δ) / 2 = (0.0325 + 0.02) / 2 = 0.02625
p10 = (p_disc − Δ) / 2 = (0.0325 − 0.02) / 2 = 0.00625
```

**Метод 1 — точный биномиальный расчёт.** Среди discordant-пар доля "успехов" (сдвиг в пользу routing): `p_succ = p01 / p_disc = 0.02625 / 0.0325 ≈ 0.808`. Для точного двустороннего биномиального теста (α=0.05) при `p_succ≈0.808` необходимое число discordant-пар для мощности 80% — `N_disc ≈ 22–24`. Переводя обратно в общий n через `n = N_disc / p_disc`: `n = 23 / 0.0325 ≈ 707`.

**Метод 2 — нормальное приближение (Connor, 1987, *Biometrics* 43(1):207-211 — стандартная формула для планирования размера выборки парного/McNemar-дизайна; практическая формула воспроизведена, например, на powerandsamplesize.com/tutorial/how-to-calculate-sample-size-mcnemars-test):**

```
n ≈ [z_(1-α/2)·√p_disc + z_(1-β)·√(p_disc − Δ²)]² / Δ²
  = [1.96·√0.0325 + 0.84·√(0.0325 − 0.0004)]² / 0.0004
  ≈ 635
```

**Метод 3 — прямая Monte Carlo симуляция точного McNemar-теста** (того же теста, что реально использует `scripts/routing_e2e_significance.py`), 3000 повторов на точку, калибровка на p_disc=0.0325/Δ=0.02: даёт n≈700-900 для мощности 80% (согласуется с методом 1).

Все три метода сходятся в диапазоне **n≈650-900 на источник** (не совпадают с общей отраслевой эвристикой MeasuringU/Lewis & Sauro, *Sample Sizes for Comparing Dependent Proportions*, measuringu.com/sample-sizes-for-the-mcnemar-test — там типовая discordant-доля из usability-исследований ≈0.22 даёт n на порядок больше (тысячи); у нашего пайплайна discordant-доля почти на порядок ниже, что и снижает требуемый n).

**Для справки, во сколько обошлась бы проверка:** парное сравнение требует ДВУХ полных end-to-end прогонов (baseline без routing + routing) на одном и том же новом наборе из ~700-800 TAT-DQA вопросов (в `eval_subset_250.parquet` их всего 123, набора не хватает) — то есть ~1400-1800 реальных вызовов Claude Sonnet 5 (generation + judge), в отличие от retrieval-only A/B, где были нужны только дешёвые embedding-вызовы Voyage AI.

### Финальное решение (2026-08-16): не масштабировать end-to-end eval

Учитывая, что (а) routing уже принят на основании retrieval-level результата, который сам по себе статистически надёжен (п. выше) и не зависит от исхода end-to-end проверки, (б) реальный бюджет проекта на Claude API ограничен и не выделен отдельно под этот вопрос, (в) прозрачный power-анализ (сколько вопросов реально нужно и почему) сам по себе демонстрирует методологическую дисциплину не хуже, чем ещё один прогон ради обнаружения эффекта в 2 п.п.: **решено не увеличивать n**. Текущее состояние (retrieval-level значим, end-to-end null при мощности ~5% на n=123, посчитанный явно требуемый n≈700-900) фиксируется как финальный результат. Если бюджет проекта расширится в будущем — прогон на TAT-DQA (только этот источник, остальные два уже чисто подтверждены на n=37/90) остаётся понятным, посчитанным следующим шагом, не требующим повторного планирования.

| 0.6 | 0.4 | 0.9320 | +0.0120 | 0/3 | 0.2500 |
| 0.7 | 0.3 | 0.9320 | +0.0120 | 1/4 | 0.3750 |

Числа монотонно растут с увеличением веса vector-ветки, и обе крайние точки (0.6/0.4 и 0.7/0.3) численно выше дефолта — но ни одна не значима (все p>0.25, discordant pairs 3-7 из 250, тест маломощен на таком количестве расхождений). **Решение: веса не меняются, остаются 0.5/0.5.** Причина — не только отсутствие значимости в отдельной точке, а то, что выбор «лучшей» из пяти протестированных точек постфактум по максимальному числу — это ровно та же data dredging ошибка, которой проект уже сознательно избежал раньше (см. п.6, эвристика «защита топ-N» для reranker'а: «порог подобран постфактум на тех же 250 вопросах, на которых измеряется, без отдельной hold-out проверки эффект недостоверен» — тот же принцип применяется здесь). Если бы направление тренда (вес vector-ветки важнее text-ветки) было содержательно интересно для дальнейшей работы — потребовалась бы отдельная hold-out выборка для проверки, не только более мощный тест на тех же 250 вопросах. Любопытный, но не доказанный побочный наблюдательный факт: тренд в сторону усиления dense-ветки противоречит направлению из T²-RAGBench (Strich et al., EACL 2026, раздел 13) и Akarsu et al. (BM25 обгоняет dense retrieval на финансовых документах) — не объяснено, не исследовалось дальше ввиду отсутствия значимости.

## 5. Contextual enrichment (этап индексации)

- **Метод:** Claude Haiku 4.5, короткая справка (1-2 предложения) на документ, prompt caching. Опциональный шаг, конфиг-флаг `enrichment.enabled`.
- **Стоимость на весь корпус:** ~$10 (экстраполяция с теста на 450 документах, $0.619 фактически, ×16.3).
- **Эффект (n=1535, hybrid retrieval, без reranker, уменьшенный корпус 450 документов):** Recall@5 0.925 → 0.933, +0.78 п.п., **значимо** (p=0.0164, 95% CI [0.20%, 1.43%]).
- **Решение:** используется. Обогащение корпуса при индексации, не на этапе запроса.
- **Важно для реализации (снимает возможную неоднозначность):** обогащение меняет `context` документа **до** индексации и эмбеддинга. Дальше по пайплайну — и retrieval, и reranker — работают с уже единым текстом (обогащённым, если `enrichment.enabled=true`), а не с двумя параллельными версиями документа. Это не развилка на этапе исполнения запроса, а последовательность: enrichment → единый текст → retrieval → reranking. (Тест аддитивности на 150 вопросах, где raw и enriched сравнивались как отдельные ветки, был инструментом измерения эффекта, не описанием архитектуры финального пайплайна.)
- **Схема документа в MongoDB (уточнено по итогам ревью, 2026-08-09):** хранить `raw_content` (исходный текст) и `contextual_summary` (справка от Haiku) отдельными полями, не только объединённый результат — полезно для отладки и на случай изменения промпта обогащения без пересчёта retrieval с нуля. Поле, по которому реально идёт поиск/reranking/подаётся в generation — `full_indexed_content` = `contextual_summary + "\n\n" + raw_content` (или пустая строка вместо summary, если `enrichment.enabled=false`). Именно это (одно) поле и есть тот "единый текст" из пункта выше.

- **Полнокорпусная валидация (закрыто 2026-08-18, временный кластер Atlas M10 `Cluster1`, удалён после прогона):** совместный эффект enrichment+reranker измерен на полном корпусе 7318 документов, 900 вопросов (300/источник), прямое парное сравнение "enriched" (`metadata_prefix+contextual_summary+raw_content`) vs "raw" (`metadata_prefix+raw_content`), оба текстовых варианта эмбеддились voyage-4, проходили через тот же hybrid retrieval (top-50) и тот же reranker (Cohere Rerank v4.0 Pro, top-5), McNemar exact test по source_dataset и overall — это тот же прямой парный тест "enriched+rerank vs raw+rerank", который предыдущая версия этого документа откладывала на потом как дешёвую, но не выполненную довеску к тесту на 150 вопросах; выполнен здесь на несопоставимо большей и полной выборке, closing that TODO:

  | source_dataset | n   | Recall@5 enriched | Recall@5 raw | Δ      | McNemar b/c | p      |
  |-----------------|-----|---------------------|----------------|--------|--------------|--------|
  | ConvFinQA       | 300 | 0.987               | 0.983          | +0.003 | 1/0          | 1.0000 |
  | FinQA           | 300 | 0.997               | 0.997          | 0.000  | 1/1          | 1.0000 |
  | TAT-DQA         | 300 | 0.973               | 0.973          | 0.000  | 1/1          | 1.0000 |
  | Overall         | 900 | 0.986               | 0.984          | +0.001 | 3/2          | 1.0000 |

  Тест был спланирован заранее (power analysis перед прогоном) для обнаружения эффекта ≥2 п.п. с мощностью ~80%; наблюдаемый эффект (+0.1 п.п. overall) на порядок меньше целевого. **Честная формулировка обязательна: на этом тесте не обнаружен эффект ≥2 п.п. — это не то же самое, что «эффекта нет».** Тест не обладает мощностью, чтобы надёжно отличить истинный эффект <1 п.п. от нуля; заявлять «enrichment не даёт эффекта на полном корпусе» было бы избыточно сильной формулировкой относительно того, что реально измерено.

  Это не опровергает статистически более ранний результат (+0.78 п.п., p=0.0164, n=1535, выше по этому разделу) — оба числа получены в разной инфраструктуре: более ранний тест — на уменьшенном корпусе 450 документов, без reranker'а; текущий — на полном 7318-документном корпусе, с reranker'ом, оба на единой voyage-4 (временный кластер намеренно не воспроизводил production per-dataset routing из п.3a, чтобы не смешивать два одновременных изменения в одном тесте). Правдоподобное объяснение расхождения — эффект потолка, не противоречие: raw-ветка полного корпуса уже даёт Recall@5=0.984 благодаря reranker'у и `metadata_prefix`, оставляя enrichment мало пространства для измеримого прироста. Это согласуется с публичным результатом Anthropic по Contextual Retrieval (engineering blog, "Introducing Contextual Retrieval"): там enrichment даёт крупный эффект именно на baseline **без** reranker'а (top-20 failure rate 5.7%→3.7%, −35%), а после добавления reranker'а к уже contextual-варианту дополнительный прирост тоже падает почти до нуля относительно уже обогащённого baseline (top-20 failure rate 2.9%→1.9%) — тот же паттерн убывающей предельной пользы enrichment поверх сильного reranked-baseline, что и здесь. Прямое количественное сравнение методологий (разный k, разный baseline — у Anthropic reranker применяется отдельно к contextual-варианту, здесь reranker общий для обеих веток) не проводилось и не должно приводиться как «такой же результат», только как согласующийся качественный паттерн.

  **Решение по enrichment не меняется:** остаётся включённым по умолчанию (`enrichment.enabled: true`). Единственный значимый измеренный эффект — +0.78 п.п. на уменьшенном корпусе без reranker'а; стоимость на весь корпус умеренная (~$10); полнокорпусный null-результат не показывает вреда от enrichment, только не подтверждает дополнительную пользу поверх уже сильного reranked-baseline при текущей мощности теста. Пересмотр этого решения по существу (выключать ли enrichment по умолчанию) — отдельная задача, не блокирует текущую документацию.

- **Открытый риск, оставшийся не закрытым:** приведённая выше полнокорпусная валидация закрывает вопрос "работает ли enrichment+reranker вместе на полном масштабе" (да, измерено, эффект не обнаружен на уровне ≥2 п.п.), но не отменяет исходную оговорку о выборке n=1535/450 документов для изолированного эффекта enrichment **без** reranker'а — то число (+0.78 п.п.) само по себе на полном 7318-документном корпусе без reranker'а отдельно не перепроверялось (полнокорпусный тест выше уже включает reranker в обеих ветках, это другое измерение). Дальнейшая перепроверка не считается приоритетной — то же практическое решение (`enrichment.enabled=true`) не зависит от исхода, а API-бюджет проекта ограничен.

## 6. Reranker

- **Модель:** Cohere Rerank v4.0 Pro (production-ключ, не trial — лимит 1000 вызовов/мес на trial уже был исчерпан один раз).
- **Размер пула:** **50** — эмпирически оптимален, не просто выбран по прецеденту статьи:

  |       Пул        | Recall@5 (n=900, точный McNemar) |            vs предыдущий                  |
  |------------------|-----------------------------------|---------------------------------------------|
  | — (без reranker) |          0.8344                   |               —                              |
  | 10               |          0.8900                   | +5.56 п.п. vs baseline, p<0.0001             |
  | 50               |          0.9444                   | +5.44 п.п. vs пул=10, p<0.0001               |
  | 100              |          0.9411                   | −0.33 п.п. vs пул=50, p=0.58 (не значимо)    |

- **Обрезка текста документа перед reranking: ЗАПРЕЩЕНА.** Это критичный, дважды подтверждённый факт: обрезка до 2000 символов (93.2% целевых документов длиннее — медиана 4263 символа) превращала прирост reranker'а в регресс (Recall@5 падал до 0.608-0.764 вместо роста). После снятия обрезки тот же reranker дал устойчивый прирост. Полный текст документа должен передаваться в Cohere API без сокращения независимо от длины.
- **Финальный Recall@5 (пул=50, без обрезки, n=900):** 0.944.

## 7. Генерация ответа

- **Формат:** Direct (прямой текстовый ответ), не Program-of-Thought.
- **Модель:** Claude Sonnet 5.
- **Обоснование (развилка 9, тест 2.4):** на 30 gold-context вопросах PoT и Direct дали одинаковое число верных ответов (0.733 = 0.733) — разрыв, который PoT показывал на Codex в 2023 (Chen et al.), с современными моделями не воспроизвёлся на этой выборке. PoT требует безопасного исполнения кода без измеримого выигрыша — не оправдано. **Оговорка по формулировке (замечание внешнего ревью):** n=30 даёт низкую мощность — точное совпадение на этой выборке не означает доказанной идентичности методов в общем случае, только отсутствие обнаруженного на этих данных разрыва. Не переформулировать как «доказано, что PoT не даёт преимущества» — только «не обнаружено преимущества на измеренных данных».
- **Критично:** сравнение сгенерированного ответа с gold-ответом должно быть **инвариантно к знаку и масштабу** (доля 0-1 vs число 0-100 для процентов). Без этой инвариантности система оценки систематически занижает реальную точность модели — баг, найденный и исправленный в тесте 2.4/2.5 (`is_close_v2`).
- **Спецификация `is_close_v2` обязательна перед кодированием (пробел, найден внешним ревью):** ТЗ ссылается на эту функцию по имени, но её точная логика (допуск относительной/абсолютной погрешности, обработка `None`/нечисловых ответов, нормализация валютных символов и единиц измерения) нигде не задокументирована — перенести буквально из рабочего Colab-скрипта теста 2.4/2.5, не переписывать по памяти. Без этого число 0.733 невоспроизводимо другим человеком. Добавить юнит-тесты с конкретными примерами (`"100"` vs `"100.0"` vs `"1.00"` как доля, `"0.5"` vs `"50%"` и т.п.) — упрощает доверие к финальным метрикам для портфолио.
- **`temperature=0.0`** на всех вызовах генерации (и здесь, и в enrichment п.5, и в судье п.8) — без этого регрессионный анализ (п.10) будет давать шум от стохастичности модели, а не только от реальных изменений пайплайна. Это касалось и прошлых тестов недель 1-2 — параметр нигде явно не был зафиксирован, при реализации исправить.

## 8. LLM Judge Evaluation (переименовано из «RAGAS evaluation» по итогам ревью, 2026-08-09 — модуль не использует библиотеку RAGAS и её метрики faithfulness/answer relevancy/context precision, только кастомный judge + `is_close_v2`, старое название создавало ложные ожидания у портфолио-рецензента)

- **Модель:** Claude Sonnet 5, единственный судья.
- **Обоснование (развилка 7, тест 2.5):** 93.3% согласия (28/30) с детерминированной проверкой на 30 вопросах; оба расхождения — один и тот же объяснимый краевой случай (не сопоставление доли и процента), не хаотичный источник ошибок. Независимый второй judge (GPT-4o-mini) не нужен.
- **Кэширование результатов судьи:** ключ `hash(question + context + answer + judge_prompt_version)` — версия промпта судьи обязательно часть ключа, не только вопрос/контекст/ответ. Без неё смена промпта судьи (например, правка формулировки инвариантности к знаку/масштабу) тихо вернёт старые оценки, посчитанные по старому промпту, и будет неотличима от «ничего не изменилось» → сохранённый score. При повторных прогонах (например, менялась только генерация для части вопросов) — не пере-судить то, что не изменилось. Экономия API-бюджета при частых регрессионных прогонах (п.10 требует делать их после каждого значимого изменения).

## 9. Критерий «готово» (развилка 8)

- **Baseline-relative контроль**, не фиксированная абсолютная планка внешних метрик. Система считается готовой, когда финальные метрики значимо (paired bootstrap/McNemar, не просто численно) превосходят собственный baseline проекта на каждом значимом изменении пайплайна — не когда достигнуто произвольное внешнее число.
- **Поправка на множественные сравнения (Bonferroni/FDR) не применяется.** Все статистические сравнения в проекте — заранее спланированные проверки конкретных архитектурных развилок, проводятся последовательно: результат одного теста определяет следующий шаг (нужен ли reranker → какой pool_size → нужен ли enrichment и т.д.), не одновременная батарея гипотез на одних данных с выбором лучшей по минимальному p-value. Каждый тест отвечает на отдельный вопрос с отдельной нулевой гипотезой — не часть одного семейства для FWER-поправки. Финальное сравнение (baseline vs итоговый пайплайн) — единственный тест, поправка не требуется по определению. При публикации сводной таблицы конфигураций в финальном отчёте — явно указать в подписи, что конфигурации тестировались последовательно, а не выбирались post-hoc по минимальному p-value.

- **Честная оговорка о накопленном числе сравнений (добавлено 2026-08-18, по итогам критического ревью проекта).** За время проекта проведено порядка 7 отдельных тестов значимости: выбор embedding-модели (п.3), reranker pool_size (п.6), эффект contextual enrichment без reranker'а (п.5), per-dataset routing на retrieval-уровне — 3 источника (п.3a), per-dataset routing end-to-end (п.3a), полнокорпусная enrichment+reranker валидация (п.5). Позиция «без поправки для заранее спланированных отдельных гипотез» (см. выше) — легитимная в статистической литературе (Rothman 1990, Saville 1990), но не единственная: традиция closed testing (Marcus/Peritz/Gabriel 1976; Westfall & Young 1993) требует поправки и для последовательных, заранее спланированных сравнений, если они относятся к одному семейству итоговых решений о конфигурации пайплайна. Это не решённый «по умолчанию корректный» вопрос, а осознанный методологический выбор с открытой, не менее авторитетной альтернативой — фиксируется здесь явно, а не оставляется подразумеваемым.

  Чтобы читатель мог сам оценить устойчивость выводов к этому выбору, а не просто поверить на слово: при наивной Bonferroni-поправке по числу тестов (~7, α=0.05/7≈0.0071) результаты с явным запасом остаются значимыми без изменений — reranker pool_size (p<0.0001), metadata_prefix (p=0.00195), TAT-DQA routing retrieval-level (p=0.0005). Результаты на грани — enrichment без reranker'а (p=0.0164) и FinQA routing (p=0.0214, который в самом п.3a уже помечен как "не устойчиво к Bonferroni" для локального сравнения из трёх источников) — под глобальной поправкой по всем ~7 тестам проекта перестают быть значимыми. Практическое следствие: архитектурные решения, где Δ был крупным (reranker, metadata_prefix, TAT-DQA routing), не зависят от выбора политики поправки; решение об enrichment (единственный эффект на грани, +0.78 п.п., p=0.0164) — единственное решение в этом документе, чья статистическая значимость зависит от того, применяется ли поправка на семью из ~7 тестов проекта. Само решение включить enrichment по умолчанию не пересматривается только на этом основании (см. п.5, полнокорпусная валидация) — но эта зависимость от выбора политики поправки не должна быть скрыта от рецензента.

## 10. Обязательные этапы оценки (не опциональные, включать в каждый релевантный модуль)

- **Диагностика ошибок по типам** до внесения изменений — не гадать, какая техника нужна, а сначала посмотреть, где именно baseline ошибается (retrieval miss / неверная таблица / генерация ошиблась).
- **Регрессионный анализ после каждого значимого изменения** — не только агрегированная метрика, а сравнение по конкретным вопросам: что было верно и стало неверно, и наоборот. Несколько раз в этом проекте именно так находились реальные баги, скрытые за стабильной или даже улучшившейся общей метрикой (пример — bge-reranker: 13 исправлено, но 44 сломано, при том что метрика могла выглядеть нейтрально).
- **Финальный ручной разбор 10-20 оставшихся ошибок**, классификация по паттернам — не ради метрики, а ради понимания (прецедент из Text-to-SQL: 91% ошибок оказались логическими и концентрировались на одной схеме).
- **Стратификация метрик по `source_dataset`** (FinQA / ConvFinQA / TAT-DQA — поле уже есть в `DocumentRecord`, модуль 1) обязательна в финальном отчёте, не только агрегированный Recall@5/accuracy по всему корпусу. Датасеты качественно разные (одношаговые числовые вопросы vs многоходовый диалог vs таблице-тяжёлые документы) — агрегат может скрывать, что пайплайн уверенно работает на одном источнике и заметно хуже на другом. Дёшево (поле уже есть, просто группировка при отчёте), но даёт содержательно более честный и сильный результат для портфолио, чем одно число.

## 11. Устойчивость к сбоям API и дедупликация (добавлено по итогам финального ревью, 2026-08-09)

- **ОБЯЗАТЕЛЬНОЕ ПРАВИЛО (добавлено 2026-08-19, см. полную формулировку и прецедент в `docs/struktura_repozitoriya.md`):** результат любого прогона с реальными платными API-вызовами (`pipeline.cli eval`, `pipeline.cli index`, скрипты из `scripts/`) должен автоматически проверяться (файлы существуют, не пусты, число записей = ожидаемому n) и копироваться на Google Drive в той же ячейке/скрипте, что его производит — не отдельным пропускаемым шагом. Нарушение этого правила один раз уже стоило проекту полностью потерянного платного прогона (`cmd_eval`, n=250, числа из README/этого документа) — данные существовали только на эфемерном диске Colab-рантайма и не пережили отключение сессии.
- **Retry с экспоненциальным backoff** на всех вызовах внешних API (Voyage, Claude, Cohere) — `tenacity`, `stop_after_attempt(5)`, `wait_random_exponential(min=1, max=60)`. Не изобретать вручную (как временные `time.sleep()` в тестовых скриптах недель 1-2) — там это было оправдано для быстрого теста, для продакшен-кода пайплайна использовать библиотеку. **Уточнение (замечание внешнего ревью):** ретраить только transient-ошибки (429 rate limit, 5xx, таймауты соединения) — не 4xx-ошибки вида 400 Bad Request, которые сигнализируют баг в самом запросе и ретраем не лечатся, только маскируют проблему повторными бесполезными вызовами.
- **`run_config.json` рядом с каждым сохранённым прогоном** (предложено дважды независимыми ревью) — snapshot конфигурации, породившей эти результаты: модель embedding, `enrichment.enabled`+модель+версия промпта, `reranker.enabled`+модель+`pool_size`, модель generation, `judge_prompt_version`. Без этого через несколько недель тестирования невозможно восстановить, какому именно прогону соответствует сохранённый набор ответов — критично для регрессионного анализа (п.10).
- **Checkpointing состояния при индексации всего корпуса** — прогресс (какие документы уже обогащены/проэмбеждены/проиндексированы) сохраняется во внешнее состояние (JSONL-файл или поле `is_indexed: true` прямо в MongoDB), не только в памяти рантайма. Тот же принцип, что уже применялся вручную во всех Colab-тестах (сохранение каждые 25-50 вопросов) — здесь формализуется как требование модулей 4 и 5, не разовый приём.
- **Без сложной асинхронности** (Celery/распределённые очереди) — не оправдано для масштаба проекта. `concurrent.futures.ThreadPoolExecutor` для батчевых вызовов API — достаточно.
- **Assert на отсутствие дубликатов** `context_id` в результатах `$rankFusion` (модуль 6) — Atlas обрабатывает это нативно, но проверка на уровне кода дешева и защищает от тихих ошибок при возможных изменениях в реализации.

## 12. Итоговая конфигурация пайплайна

```
Ingestion (FinQA+ConvFinQA+TAT-DQA)
  → Chunking (формат датасета, без отдельной сериализации таблиц)
  → Contextual enrichment (Claude Haiku 4.5, опционально по конфигу)
  → Embedding (Voyage-4, эмбеддится full_indexed_content — уже с учётом enrichment, если включён)
  → Indexing (MongoDB Atlas: vector_index_full + text_index_full)
  → Hybrid retrieval ($rankFusion, top-50)
  → Reranking (Cohere Rerank v4.0 Pro, пул=50, полный текст, top-5)
  → Generation (Direct, Claude Sonnet 5, знак/масштаб-инвариантный формат)
  → LLM Judge Evaluation (Claude Sonnet 5 judge + детерминированная кросс-проверка)
```

**Итоговый Recall@5 (retrieval-часть, n=900, полный корпус): 0.944.**

Все компоненты (reranker, enrichment, judge, embedding, pool_size) должны быть переключаемы через конфиг, не хардкод — см. `3.3 Структура репозитория`.

## 13. Сравнение с опубликованными результатами (добавлено 2026-08-18)

**T²-RAGBench (Strich et al., EACL 2026 — [aclanthology.org/2026.eacl-long.8](https://aclanthology.org/2026.eacl-long.8/))** — статья, представившая сам датасет. Её abstract сообщает retrieval-level находки (Hybrid BM25 — «наиболее эффективный подход для этих данных»), не end-to-end точность генерации ответа — не источник для сравнения judge accuracy. Полный текст статьи не разбирался построчно (только abstract) — если там есть numeric baseline для generation accuracy, здесь это не учтено; утверждение «сравнения не найдено» относится к тому, что удалось найти веб-поиском и разбором abstract, не к исчерпывающему прочтению статьи.

**Akarsu, Karaman, Mierbach, "From BM25 to Corrective RAG: Benchmarking Retrieval Strategies for Text-and-Table Documents" (arXiv:2604.01733, апрель 2026)** — бенчмаркает десять retrieval-стратегий на том же самом датасете T²-RAGBench (23 088 вопросов, 7 318 документов) — уже использовалась как точка сравнения при закрытии развилки 2 (reranker) в неделе 2, см. `poshagovyi_plan_vypolneniya.md`. Числа статьи перепроверены веб-поиском 2026-08-18 независимо от собственных заметок проекта (не просто пересказаны по памяти):

| Конфигурация | Recall@5 (Akarsu et al.) | Recall@5 этого проекта |
|---|---|---|
| Только BM25 | 0.644 | отдельно не тестировался |
| Только dense | 0.587 | отдельно не тестировался |
| Hybrid RRF (BM25 + dense) | 0.695 | 0.808 (n=250, полный корпус) |
| Hybrid + Cohere Rerank v4.0 Pro | 0.816 | 0.944 (n=900, полный корпус) |

**Честная интерпретация разницы (+11.3 п.п. на hybrid, +12.8 п.п. на hybrid+reranker):** это не заявка на превосходство алгоритма — retrieval-архитектура (гибрид BM25+dense через `$rankFusion`, Cohere Rerank v4.0 Pro поверх) идентична описанной в статье. Два наиболее вероятных источника разницы, оба уже задокументированы в этом ТЗ отдельными развилками, а не введены задним числом специально для этого сравнения:
1. **Отсутствие обрезки текста документа перед reranking** (п.6) — собственный тест проекта дважды подтвердил, что обрезка до 2000 символов превращает прирост reranker'а в регресс. В статье Akarsu et al. политика обрезки текста не указана явно (не найдена в доступных фрагментах) — нельзя утверждать, что они обрезали текст, только что этот параметр у них не задокументирован, а у нас — задокументирован и явно отключён.
2. **`metadata_prefix`** (упоминается в README, закрывает лексический разрыв между переформулированными вопросами T²-RAGBench и индексируемым текстом) — даёт +5.2 п.п. сам по себе (Recall@5 0.896→0.948, n=250, McNemar p=0.00195), измерено отдельно от reranker'а и enrichment.

**Ограничение сравнения, не скрывать:** числа этого проекта — на стратифицированной подвыборке n=250 (hybrid baseline) и n=900 (с reranker'ом), не обязательно на той же eval-выборке, что использовали Akarsu et al. (размер их конкретной eval-выборки не установлен из доступных источников — датасет целиком 23 088 вопросов, но benchmark обычно считается на test-сплите, не на всём датасете). Доверительные интервалы для их чисел не опубликованы в найденных фрагментах — прямое статистическое сравнение (напр. z-test двух пропорций) не проводилось, только сопоставление точечных оценок.

**End-to-end точность генерации — более слабое сравнение.** Прямой публикации, бенчмаркающей generation accuracy на объединённом T²-RAGBench split, не найдено. Ближайший найденный ориентир — **FinAgent-RAG (arXiv:2605.05409)**, агентный Program-of-Thought пайплайн с self-verification, оценённый отдельно на трёх исходных датасетах (не на объединённом T²-RAGBench-сплите): execution accuracy 76.81% (FinQA), 78.46% (ConvFinQA), 74.96% (TAT-QA).

| Источник | Judge accuracy (этот проект, n=250) | Execution accuracy (FinAgent-RAG) |
|---|---|---|
| FinQA | 0.711 | 0.7681 |
| ConvFinQA | 0.865 | 0.7846 |
| TAT-DQA / TAT-QA | 0.780 | 0.7496 |
| Overall | 0.768 | не сообщается в едином числе в найденных фрагментах |

*(См. уточнение ниже: колонка FinAgent-RAG опирается на статью, впоследствии отозванную автором — все три числа читать как иллюстративный ориентир, не как подтверждённый baseline.)*

*(Числа этого проекта в таблице — из прогона, не сохранённого на момент публикации этого раздела; независимо подтверждены повторным, сохранённым прогоном 2026-08-19 в пределах 1-3 п.п. на источник — см. п.14.)*

Этот проект впереди на ConvFinQA и TAT-DQA, позади на FinQA. **Почему это сравнение слабее retrieval-сравнения выше, явно, не подразумеваемо:**
- Разные eval-выборки и их размер (наш n=250 фиксированный стратифицированный сплит; размер и состав выборки FinAgent-RAG из доступных фрагментов не установлен).
- Разная методология скоринга: execution accuracy (обычно — точное совпадение после исполнения сгенерированной программы) vs LLM-судья + детерминированная кросс-проверка (`is_close_v2`, инвариантная к знаку/масштабу) этого проекта — не гарантированно один и тот же критерий «правильно».
- Разная архитектура генерации: FinAgent-RAG — агентный PoT с self-verification (Program-of-Thought устраняет, по их заявлению, 88.0% арифметических ошибок); этот проект — Direct (прямой текстовый ответ), выбор обоснован в п.7 отдельным измерением (0.733=0.733 на 30 вопросах, без обнаруженного преимущества PoT на используемой модели) — разные архитектурные развилки, решённые независимо, не заимствование одна у другой.

**Уточнение (2026-08-28): FinAgent-RAG отозвана автором.** Проверено напрямую на странице arXiv (`arxiv.org/abs/2605.05409`, скриншот страницы) — статус документа: «Отозвано» (Withdrawn), автор отзыва — Ян Шу, последняя редакция страницы — 5 июля 2026 (v2); конкретная причина отзыва на самой странице не указана (текст «Данная статья была отозвана Ян Шу» — русский перевод интерфейса arXiv, не дословная цитата из тела статьи). Это не доказывает, что числа статьи (76.81%/78.46%/74.96%) неверны — но они больше не являются подтверждённым опубликованным ориентиром, на который можно ссылаться как на действующий результат. Практическое следствие для вывода ниже касается **всех трёх** чисел таблицы одинаково, не только FinQA: и «этот проект позади» (FinQA), и «этот проект впереди» (ConvFinQA, TAT-DQA) — все три сравнения опираются на один и тот же отозванный ориентир и одинаково теряют доказательную силу; выборочно смягчать только неудобное для проекта сравнение было бы нечестно. Архитектурное и методологическое объяснение разницы (PoT/self-verification vs Direct, execution accuracy vs LLM-judge+`is_close_v2`, разные eval-сплиты) остаётся в силе независимо от отзыва — оно не строилось на предположении о корректности цифр FinAgent-RAG.

**Вывод по разделу:** retrieval-часть пайплайна показывает воспроизводимое, статистически измеренное превосходство над одной прямой публикацией на идентичном датасете (Akarsu et al., не затронута отзывом), с правдоподобным инженерным объяснением разницы (не алгоритмическим). End-to-end сравнение — только направленный ориентир, не строгое доказательство конкурентоспособности с агентными системами, и вдобавок целиком опирается на впоследствии отозванную публикацию (см. уточнение выше, касается всех трёх пар чисел, не только FinQA); для строгого сравнения потребовался бы прогон обеих систем на одном и том же eval-сплите с одной и той же методологией скоринга против действующей, не отозванной публикации — что не сделано и не планируется в рамках этого проекта.

### Разбор ошибок: что доступно для анализа и что нет

**Ограничение, обязательное к указанию:** `predictions.jsonl` содержит `question_id`, `question`, `source_dataset`, `gold_answer`, `answer_text` — не сохраняет id/содержимое реально извлечённых top-5 чанков после reranking. Это значит, что по этим двум файлам **нельзя достоверно отличить retrieval-ошибку (нужный документ не попал в top-5) от generation-ошибки (документ был в контексте, но модель посчитала/извлекла из него неверное число)** — классификация ниже основана только на сопоставлении gold-ответа и текста ответа модели, не на инспекции контекста. Для точной атрибуции retrieval vs generation в будущем прогоне `run_config`/pipeline стоит сохранять id извлечённых документов вместе с предсказанием — не сделано в этом прогоне, фиксируется как пробел на будущее, не восполняется задним числом.

**Закрыто в коде 2026-08-20** (план доработки после экспертизы, пункт 2): `pipeline/cli.py cmd_eval()` теперь пишет в `predictions.jsonl` дополнительное поле `retrieved_docs` для каждого из top-N документов после reranking (тех же объектов, что уходят в generation), плюс то же поле в `generation_checkpoint.jsonl` для устойчивости к прерыванию прогона. Это касается только будущих прогонов — сам прогон `error_analysis_250` (и таксономия 60 ошибок ниже) выполнен до этого изменения и задним числом не переразбирается, по тому же правилу "не восполняется задним числом".

**Пересмотрено в коде 2026-08-20** (план доработки-2 по итогам внешней экспертизы, пункт 1, "компактный evidence trace"): формат `retrieved_docs` изменён с `{"context_id", "full_indexed_content"}` на компактный `{"context_id", "rank", "score", "content_sha256"}` — без копии полного текста чанка. Полный текст уже хранится как authoritative source в MongoDB по `context_id`; дублирование его в `predictions.jsonl`/`generation_checkpoint.jsonl` не даёт дополнительной ценности и создаёт вторую, потенциально расходящуюся копию того же контента. `content_sha256` — хеш SHA-256 от `full_indexed_content` на момент прогона — позволяет впоследствии проверить, что документ с данным `context_id` в MongoDB действительно тот же самый, что был реально извлечён во время прогона (например, после переиндексации или миграции embedding). `rank` — 1-индексированная позиция в итоговом (пост-rerank) списке, то есть тот же порядок, в котором документы попадают в `context` для generation. Реализация: `pipeline/cli.py`, `_retrieved_docs_for_prediction()`; тесты — `tests/test_cli.py`.

| Смена знака при верном порядке величины | 1 | 1.7% | `tatqa_train_4978`: gold=-7.64, ответ=8.43 — величина близка, знак противоположный |
| Формат ответа не соответствует вопросу | 1 | 1.7% | `tatqa_train_3621`: вопрос просил количество категорий (gold="2"), модель вернула названия категорий текстом — не числовая ошибка, ошибка следования инструкции формата |

**По источникам:** TAT-DQA — 29 ошибок из 60 (48%, при этом TAT-DQA даёт только 49% вопросов выборки — пропорционально), FinQA — 25 (42%, при 36% вопросов выборки — непропорционально много), ConvFinQA — 6 (10%, при 15% вопросов выборки — непропорционально мало). Согласуется с accuracy по источникам выше: FinQA — самый слабый источник этого прогона.

**Примеры «близкого промаха»** (контекст, вероятно, верный, ошибка в вычислении/выборе периода): `finqa_dev_569` (gold=193, ответ=192 — расхождение на 1), `tatqa_train_8832` (gold=119655.67, ответ=118989.67 — среднее посчитано по другой паре периодов), `tatqa_train_1740` (gold=50158.67, ответ=50226.67).

**Примеры явного отказа при наличии ответа в датасете:** `finqa_dev_788`, `finqa_train_4449`, `finqa_train_2391`, `tatqa_train_4974`, `tatqa_train_4256`, `tatqa_train_8524`, `tatqa_train_8525` — 4 из 7 на TAT-DQA, что содержательно совпадает с самым слабым источником по recall в п.3a (TAT-DQA исторически требовал отдельного embedding-routing именно из-за таблице-тяжёлых документов).

### Отдельная находка: несогласия LLM-судьи и детерминированной проверки (`is_close_v2`)

15 из 250 вопросов (6%) — случаи, где `deterministic_match` (`is_close_v2`) и вердикт судьи разошлись. Это отдельная ось анализа — не ошибка пайплайна генерации, а вопрос о качестве самой eval-инфраструктуры (уже помечен как открытый пробел в п.7: «точная логика `is_close_v2` … нигде не задокументирована»). Итоговая метрика accuracy проекта использует `judge_correct` (более мягкий и обычно более содержательно верный сигнал, см. п.8), поэтому эти случаи уже учтены корректно в headline-числах — но сам факт разногласий стоит зафиксировать как диагностику качества `is_close_v2`:

- **10 из 15 — судья мягче, чем `is_close_v2`** (детерминированная проверка не засчитала, судья засчитал). Доминирующий паттерн (8 из 10) — представление величины в другом порядке (тысячи/миллионы/сырое число): `convfinqa_2441` (1832000 vs 1832), `tatqa_train_6808` (14100000 vs 14.1), `tatqa_train_8052` (3550 vs 3550000000), `tatqa_train_6526` (44458 vs 44458000), `tatqa_train_8931` (181401 vs 181401000), `tatqa_train_8556` (2100000 vs текст "2.1 million"), плюс два случая текстового формата года (`tatqa_train_5894`, `tatqa_train_8367`: gold="2019.0" vs ответ "Year-ended 31 March 2019") и один булев формат (`finqa_dev_656`: gold="0" vs ответ "No"). **Вывод: `is_close_v2` не распознаёт единицы измерения и текстовые форматы, которые семантически эквивалентны gold-ответу — известное и теперь конкретно подтверждённое ограничение**, актуальное для п.7 (там уже отмечено, что спецификация `is_close_v2` не задокументирована и должна включать явную обработку единиц измерения).
- **5 из 15 — судья строже, чем `is_close_v2`** (`is_close_v2` засчитал совпадение, судья не согласился): `finqa_dev_569`, `finqa_dev_451`, `finqa_train_2226`, `tatqa_train_8832`, `tatqa_train_1740`. Три из пяти (`finqa_dev_451`, `finqa_train_2226`, и частично паттерн ×100) — случаи, где `is_close_v2`, по всей видимости, слишком охотно принимает представление «доля vs проценты» (×100) как совпадение, даже когда по существу вопроса это разные числа — подозрение на false positive в допуске `is_close_v2`, не в судье.

### Что это значит для проекта

1. **Основной источник ошибок (65% от всех ошибок) — необъяснённые сильные расхождения**, которые не удаётся дальше классифицировать без сохранённого контекста извлечения. Это конкретный, обоснованный аргумент в пользу добавления id/содержимого retrieved-документов в `predictions.jsonl` будущих прогонов — не абстрактное пожелание, а прямое следствие того, что 39 из 60 ошибок в этом разборе остались неклассифицированными по причине отсутствия этих данных.
2. **`INSUFFICIENT_CONTEXT` (12% ошибок), непропорционально сконцентрированный на TAT-DQA**, — согласуется с уже известной слабостью пайплайна на таблице-тяжёлых документах (п.3a, п.6) и не противоречит прежним находкам.
3. **`is_close_v2` содержит как минимум два конкретных, теперь задокументированных класса неточности** (не распознаёт единицы измерения/текстовые форматы; возможные false positives на ×100-совпадениях) — не блокирует текущие headline-метрики (судья используется как основной сигнал), но должно быть учтено при следующей ревизии `is_close_v2`, если она случится.
4. **Явных признаков систематической ошибки reranker'а или embedding-routing в этом разборе не обнаружено** — ошибки распределены по разным типам вопросов и источникам без явного паттерна одной сломанной подсистемы (в отличие, например, от исторического прецедента bge-reranker в п.10, где конкретная поломка была видна в регрессионном сравнении по вопросам). **Подтверждено количественно в разделе 21 (пункт 7 плана-2, retrieval/generation attribution, 2026-08-21):** из этих 60 ошибок только 5 (8.3%) объясняются провалом retrieval/reranking, 55 (91.7%) произошли при том, что gold-документ уже был в контексте генерации — retrieval/reranking не узкое место пайплайна.

**Следующий шаг по явно оговорённому порядку работ:** внешняя экспертиза всего проекта — не начата, требует отдельного скоупинга.

## 16. Latency: замер по стадиям (добавлено 2026-08-21, план доработки-2, пункт 2)

**Контекст.** В отличие от cost (раздел 15), latency нельзя посчитать по прайсингу — нужен реальный замер. До этого изменения в проекте не было ни одного замера времени: `cmd_eval()` — полностью последовательный цикл (retrieval → rerank → generation, затем отдельным проходом judge), без `concurrent.futures.ThreadPoolExecutor`, несмотря на то что эта библиотека упомянута как доступный инструмент в разделе 11.

**Реализация.** `pipeline/common/latency.py` (`summarize_latencies()`, `write_latency_report()`) + инструментация в `pipeline/cli.py cmd_eval()` (`time.perf_counter()` вокруг вызовов `retrieve()`, `rerank()`, `generate_answer()`) и в `pipeline/evaluation.py evaluate_answers()` (новый опциональный параметр `latency_sink`, засекает только реальные вызовы judge). Замеряются **только реальные API-вызовы этого прогона** — вопрос, восстановленный из `generation_checkpoint.jsonl` (уже отвечен в прошлом прогоне) или найденный в judge-кэше, не учитывается: и то, и другое занимает микросекунды и исказило бы числа в сторону заниженных, если бы попало в выборку наравне с реальными вызовами.

**Формат.** `results/<run_id>/latency_report.json` — по стадиям (`retrieval_s`, `rerank_s`, `generation_s`, `judge_s`): `n`, `mean_s`, `median_s`, `p95_s` (метод nearest-rank), `min_s`, `max_s`, `total_s`. Стадия без единого измерения за прогон (например, reranker отключён в конфиге, либо все вопросы пришли из чекпоинта) — явно `null`, не подставленный 0: тот же принцип "нет данных ≠ данные со значением 0", что уже используется в разделе 15 для output-токенов (измерено/предположено/исследовано). Та же сводка попадает в `eval_report.md` (секция "## Latency") и печатается в stdout по завершении прогона.

**Числа появятся после следующего реального прогона** — на момент написания этого раздела инструментация готова и покрыта тестами (`tests/test_latency.py`, `tests/test_evaluation.py`, `tests/test_cli.py`), но ни одного платного прогона под новым кодом ещё не было; задним числом посчитать latency для уже закоммиченного `results/error_analysis_250` нельзя — время API-вызовов нигде не логировалось на момент того прогона.

## 18. Human-калибровка LLM-judge (добавлено 2026-08-21, план доработки-2, пункт 4)

**Контекст.** До этого раздела судья (Claude Sonnet 5) сверялся только с автоматическим детерминированным чекером (`is_close_v2`) — 93.3% согласия (28/30), см. раздел 8 — но ни разу не сверялся с реальной человеческой разметкой. Мотивация — прямо документированная находка `joaopaulotr/financebench-rag-eval` (раздел 17): их первая версия LLM-судьи показала +16 п.п. "fluency bias" (номинальная точность 63/100 против человеческой калибровки ~47/100) — судья систематически завышал точность, засчитывая бегло написанные, но численно неверные ответы. Без собственной человеческой проверки нельзя было исключить тот же эффект в этом проекте, при том что итоговые 76.0-76.8% целиком опираются на вердикт судьи.

**Метод.** 30 вопросов выбраны случайной выборкой (Python `random.Random(20260821)`, фиксированный seed) из прогона `results/error_analysis_250`, стратифицированно, пропорционально составу полного корпуса: TAT-DQA 15, FinQA 11, ConvFinQA 4 (округление до целого от долей 49.2%/36.0%/14.8%). Виктор размечал вопросы вручную, **вслепую** — ни вердикт судьи, ни результат `is_close_v2` не показывались во время разметки (хранились отдельно, `answer_key.json`, не отправлялся пользователю), чтобы разметка не подстраивалась под уже вынесенный судьёй вердикт. Критерий совпадения для разметки — дословно тот же, что в `JUDGE_PROMPT` (округление, знак при неоднозначном направлении, проценты vs доли, разные единицы одного значения), чтобы сравнение было по одной и той же линейке, а не по более строгому или более мягкому человеческому стандарту. ## 21. Пункт 7 плана-2: retrieval/generation attribution — код и реальные числа (добавлено 2026-08-21, числа получены 2026-08-21)

**Контекст.** План-2 сформулировал пункт 7 как «FinQA-only `gold_inds` → `context_id` attribution — только эксперимент, только если пункты 1-6 сделаны и остаётся время/бюджет» — по рекомендации ChatGPT-документа, где отдельно подчёркивалось: официальный FinQA-датасет даёт `gold_inds` (sub-document supporting facts), а ConvFinQA/TAT-DQA такого поля вообще не предоставляют — поэтому единый классификатор на все три источника даст ложную точность, и attribution стоит делать только для FinQA.

**Найденная и проверенная поправка к этой посылке.** При реализации выяснилось, что эта посылка не применима к данным именно этого проекта — не потому, что ChatGPT ошибся про сами датасеты, а потому что архитектура пайплайна работает на другой гранулярности. Чанкинг проекта — «один документ = один чанк» (см. `README.md`, Architecture); `data/t2-ragbench/eval_subset_250.parquet` (как и все три исходных parquet-файла T²-RAGBench — проверено для FinQA/ConvFinQA/TAT-DQA) уже содержит колонку `context_id` — по одному значению на строку/вопрос, для всех трёх источников без исключения, не только для FinQA. Это подтверждено прямой инспекцией `pipeline/ingestion.py` (строки 44-49, 168): именно это поле `context_id` — тот же самый идентификатор, под которым документ индексируется в MongoDB и по которому retrieval/reranking его находят. То есть проблема, о которой предупреждал ChatGPT-документ («`gold_inds` — это не то же самое, что ваш `context_id`, нужен отдельный мэппинг, и не факт, что дёшево»), возникает только на суб-документной гранулярности (например, если бы чанкинг был по абзацам/строкам таблицы) — при document-level чанкинге этого проекта `gold_context_id` для любого вопроса — это буквально значение колонки `context_id` того же вопроса, без всякого мэппинга, и одинаково доступно для FinQA, ConvFinQA и TAT-DQA.

**Практическое следствие: пункт 7 расширен на все три источника**, не только FinQA — с тем же принципом однократной, не универсальной по грануларности логики, который ChatGPT сам защищал (не строить «умный» классификатор поверх разнородной суб-документной семантики трёх датасетов) — здесь классификатор универсален только потому, что сама единица гранулярности (документ) для всех трёх источников одна и та же, а не потому, что игнорируются их различия.

**Что реально блокирует получение чисел.** Ни `results/error_analysis_250` (прогон предшествует какому-либо сохранению retrieval-провенанса), ни какой-либо `eval`-прогон до этого изменения не сохраняют top-50 пул **до** reranking — только post-rerank top-5 (`retrieved_docs`, см. `_retrieved_docs_for_prediction`, пункт 1 плана-2). Без top-50 нельзя различить `retrieval_failure` (gold-документ не попал даже в пул кандидатов) от `reranking_failure` (попал в пул, но reranker его не оставил в топ-5) — а это и есть основная ценность attribution. Досчитать это задним числом для уже закоммиченного прогона нельзя (тот же принцип «не восполняется задним числом», что и в разделе 14).

**Реализовано (код, тесты — без единого платного API-вызова):**
- `pipeline/cli.py`: новый флаг `eval --retrieval-only` — прогоняет только retrieval+reranking (модули 6-7), пропускает generation и judge полностью. Пишет `results/<run_id>/retrieval_trace.jsonl`: по одной строке на вопрос, `{question_id, source_dataset, candidate_top50, reranked_top5}` — оба поля в том же компактном формате `{context_id, rank, score, content_sha256}`, что уже используется для `retrieved_docs` (переиспользована та же функция `_retrieved_docs_for_prediction`, вызванная дважды — на `candidates` (пул=50, до rerank) и на `ranked` (топ-5, после rerank)). Никакого чекпоинта/resume здесь нет: retrieval-only прогон быстрый (без LLM-вызовов) и дешёвый, поэтому при сбое разумнее перезапустить с нуля, чем усложнять код ради resume ради нескольких сотен rerank-вызовов.

## 22. Пункт 8 плана-2: Architectural Trade-offs / retrieval-прогрессия (добавлено 2026-08-21)

**Контекст.** ChatGPT-документ рекомендовал две визуальные добавки поверх уже существующих таблиц: (1) дерево «что рассматривали → от чего отказались» — по его же формулировке, «самая ценная идея во всём анализе», поскольку явно показывает не только принятые решения, но и отклонённые альтернативы; (2) «baseline ladder» — Dense → BM25 → Hybrid → +Reranker → +Enrichment → Final, с Recall@5/latency/cost на каждой ступени.

**Проверка перед реализацией и почему ladder сделан не буквально по рекомендации.** Прямая проверка данных проекта показала, что предложенный ChatGPT ladder нельзя честно построить в буквальном виде: (а) Dense-only и BM25-only по отдельности в этом проекте никогда не измерялись — только hybrid с sweep весов от 0.3/0.7 до 0.7/0.3 (раздел 4), крайние точки 0/1 и 1/0 не тестировались; (б) latency по стадиям (пункт 2 плана-2) ещё не измерен — ни одного платного прогона под новой инструментацией не было (раздел 16); (в) разные измеренные числа Recall@5 в проекте относятся к разным n/корпусам/конфигурациям (n=250 без reranker'а на полном корпусе; n=900 с per-dataset routing; n=1535/450-документов для изолированного эффекта enrichment без reranker'а) — свести их в один непрерывный ряд означало бы визуально подразумевать единый контролируемый эксперимент там, где его не было, что противоречит принципу проекта «не выдавать расчётное/разнородное за измеренное в одном тесте».

**Что сделано вместо буквального ladder.** В README (все 3 языка), после таблицы «Key decisions», добавлены два новых блока:
1. **«Considered and rejected»** — компактный список альтернатив, которые были протестированы или оценены и осознанно не приняты, каждая с уже существующим числом/источником: PoT (n=30, тай 0.733=0.733), веса fusion 0.6/0.4 и 0.7/0.3 (p>0.25 везде), пул reranker'а=100 (p=0.58), масштабирование TAT-DQA до n=700-900 (оценка $23-29 — по карману, но не сделано по причине, не связанной с ценой), полный редизайн `is_close_v2` (отклонено как смена scope, не техническая доработка), Docker/FastAPI/observability-обвязка (не закрывает реальный пробел проекта).

Это прямо указывает направление Фазы 5: вмешательство, требующее explicit-цитирования конкретной строки/периода перед вычислением плюс финальный self-check «пересчитай и сверь», должно бить именно по этим 15/25 (60%) случаев, а не быть общим косметическим изменением промпта. Категория C (3/25) требует другого вмешательства (явное требование указывать базу дроби и знак направления изменения) — уже заложено в план Фазы 5 как отдельный пункт. Категории B, H, J — не предвиденные планом, но каждая по 1-2 случая: не образуют самостоятельного приоритета, но дают конкретные формулировки для промпта («если в контексте несколько сущностей — явно назови выбранную», «не меняй уже вычисленный результат без нового факта из текста», «если число в тексте единственное и однозначное — не отказывайся из-за посторонней неточности формулировки вопроса»).

**Ограничение.** Категоризация A/D для случаев без точного числового доказательства (не отмечены как «подтверждено математикой» в таблице выше) — прочтение raw_response и правдоподобие по масштабу расхождения, не построчная сверка с parquet-источником. Общее распределение (доминанта A+D=60%) устойчиво к отдельным ошибкам классификации на границе A/D (обе ведут к одному вмешательству Фазы 5), но точный процент по каждой из них по отдельности может измениться на 1-2 случая при более глубокой проверке — это не блокирует переход к Фазе 5.

**Реализация.** Эта таксономия не меняет `failure_stage`/`manual_correction_phase*` — все 25 случаев остаются `generation_failure_candidate`, здесь фиксируется только причина, а не статус. Полное обоснование по каждому вопросу с raw_response — `results/retrieval_trace_250/generation_failure_traces.jsonl` (уже в репозитории с Фазы 3).

## 28. Фаза 5 — два целевых вмешательства в промпт генерации, готовы к A/B (Фаза 6) (добавлено 2026-08-23)

**Контекст.** Продолжение раздела 27. По правилу Фазы 6 «один вариант вмешательства — один скрипт — одна проверка» (`claude/plan_generation_error_analysis.md` в проекте) вмешательства спроектированы как два ОТДЕЛЬНЫХ варианта промпта, не один объединённый — иначе по итогам A/B-теста нельзя будет сказать, какое именно изменение сработало.

**`pipeline/generation.py`, `PROMPT_TEMPLATE_CITE_AND_CHECK`** — таргет: категории A (не та строка/столбец/сущность, 10/25), D (неполное вычисление, 5/25), B (многосущностная неоднозначность, 2/25), H (отменённый верный результат, 1/25), J (необоснованный отказ, 1/25) — суммарно 19/25 (76%). Требует явно процитировать документ/строку/столбец/период/сущность для каждого используемого числа ДО вычисления, явно назвать выбранную сущность при неоднозначности, пересчитать результат перед выдачей и не отменять уже верно вычисленное значение без нового факта из текста. Два конкретных случая из раздела 27 прямо мотивируют формулировку: `finqa_train_6044` сам написал в рассуждении «Document 2 (2016 report)», хотя вопрос про 2018 — требование назвать период ДО использования числа поймало бы это; `finqa_train_2917` сам верно посчитал 0.50, а затем передумал без новых фактов — этому напрямую противоречит новое правило.

**`pipeline/generation.py`, `PROMPT_TEMPLATE_FORMULA_BASE`** — таргет: категория C (ошибка знака/базы формулы, 3/25, 12%), подтверждено точной математикой в разделе 27, а не предположением. Требует явно проговорить числитель и знаменатель дроби словами перед вычислением ratio/процента и сохранять знак направления изменения («decrease» → отрицательное число) в финальном ответе.

Оба варианта не меняют контракт `FINAL ANSWER: <value>` — `_extract_final_answer()` работает одинаково независимо от варианта промпта (проверено тестом `test_every_prompt_variant_keeps_the_final_answer_contract`).

**Реализация (код, без единого платного вызова API):**

- `pipeline/generation.py`: `PROMPT_TEMPLATE` (сам baseline-промпт) не тронут; добавлены `PROMPT_TEMPLATE_CITE_AND_CHECK`, `PROMPT_TEMPLATE_FORMULA_BASE`, словарь `PROMPT_TEMPLATE_VARIANTS = {"baseline": ..., "cite_and_check": ..., "formula_base": ...}`. `build_prompt()`/`generate_answer()` получили необязательный параметр `template`, по умолчанию `PROMPT_TEMPLATE` — существующие вызовы (production eval) не меняют поведение без явного выбора варианта.

## 29. Правило сохранения долгих платных прогонов — реализовано в коде перед Фазой 6 (добавлено 2026-08-24)

**Контекст.** Перед первым платным прогоном Фазы 6 пользователь напомнил о правиле, закреплённом отдельным документом «Правила сохранения долгих платных прогонов» (загружено в проект как `claude/pravila_sohraneniya_dolgih_platnyh_progonov.md`) — расширенной версии правила п.11/`struktura_repozitoriya.md` (2026-08-19), написанной по итогам ВТОРОГО инцидента: уже после того, как первая версия правила («проверить → скопировать на Google Drive → закоммитить») была формально соблюдена, следующий скрипт всё равно потерял надёжность — путь для копирования на Drive был захардкожен в самой Colab-ячейке по памяти, с опечаткой в регистре (`rag-project` вместо реального `RAG-project`), и проверка после сохранения сверяла только «файлы существуют и не пусты по тому пути, куда мы их положили», а не «мы положили их туда, куда собирались». Файлы физически ушли в новую директорию-двойник, а не в реальное дерево результатов.

**Обязательная архитектура из правила** (не просто текстовая памятка — минимизация мест, где путь/логика сохранения можно набрать заново):

1. Канонический путь — одна константа, заданная один раз, не перепечатываемая в каждом скрипте.
2. Одна тестируемая функция сохранения, переиспользуемая, не переизобретаемая заново.
3. Финальные файлы прогона копируются в постоянное хранилище в той же ячейке/скрипте, что их производит.
4. Перед созданием новой директории — проверка существующих без учёта регистра; при похожем совпадении — использовать его и явно сообщить, не создавать двойник молча.
5. Проверка после сохранения сверяет САМ ПУТЬ (совпадает с канонической константой), не только наличие/непустоту содержимого.
6. Итоговый абсолютный путь печатается явно и крупно в конце выполнения.
7. Жёсткая проверка полноты результата (файлы существуют, не пусты, число записей = ожидаемому) — `raise`, не `print`.
8. Только после пп.1-7 результат готов к коммиту.

**Реализация (код, без единого платного вызова API):**

- `pipeline/common/persist.py` — новый модуль, единственная точка сохранения/верификации для всего проекта: `verify_run_files()` (п.7 — жёсткая проверка существования/непустоты/точного числа строк, `raise RunVerificationError` со списком ВСЕХ найденных проблем, не только первой), `find_canonical_root()` (пп.4/5 — подтверждает, что канонический путь существует именно так, как сконфигурирован; если рядом найдена директория с тем же именем в другом регистре — `raise PersistPathMismatchError` с явным указанием на неё, а не тихое создание нового дерева; это прямая защита от бага инцидента №2, воспроизведённого в тестах), `save_run_to_drive()` (пп.2/3/5/6 — копирует, затем resolve()-ит путь копии и проверяет, что она действительно внутри канонического корня, затем печатает итоговый путь крупно).
- `config/config_schema.py` — новая секция `PersistenceConfig.google_drive_results_dir`, дефолт `/content/drive/MyDrive/RAG-project/results` (регистр — как уже реально создано на Drive, `notebooks/experiments_weeks_1_2.ipynb`). Явно прописана в `config.yaml`, `config_cite_and_check.yaml`, `config_formula_base.yaml` — путь виден и правится в конфиге, не в коде.
- `scripts/run_phase6_ab_eval.py` — новый скрипт по устоявшемуся в проекте паттерну (`scripts/run_eval.py`: константы в начале файла, `cli.main([...])`, без argparse). Считает реальное число вопросов из parquet-файла программно (не по памяти — тот же принцип «не хардкодить», что и для пути), запускает `pipeline.cli eval`, затем `verify_run_files()` и `save_run_to_drive()` из нового модуля. Важная оговорка к самому методу: одиночный вызов и повторные 3–15 вызовов — это ОДИН и тот же judge (та же модель, тот же промпт, температура 0.0), только с разным числом повторов. Повтор гасит случайный шум одного вызова, но не отделён от систематического смещения самого judge — если у него есть систематическая ошибка, она одинаково присутствует и в одиночном, и в повторном варианте. По-настоящему независим от judge только третий столбец (`is_close_v2`).

| Пара | p (одиночный judge, выше) | p (judge, 3–15 вызовов, тот же judge) | p (`is_close_v2`, независимо от judge) |
|---|---|---|---|
| baseline vs cite_and_check | 1.0000 | 0.5078 | 1.0000 |
| baseline vs formula_base | 0.5488 | 0.1797 | 0.2101 |
| cite_and_check vs formula_base | 0.5078 | 0.7266 | 0.2266 |

Это не закрывает вопрос мощности теста (n=250 не менялся, небольшой истинный эффект по-прежнему может остаться незамеченным) и не является тройной независимой проверкой в строгом смысле — первые два столбца используют один и тот же инструмент. Но ключевое здесь — согласие именно третьего, по-настоящему независимого от judge столбца с первыми двумя: если бы вывод «нет значимой разницы» был артефактом смещения этого конкретного judge, у метода без единого обращения к LLM не было причин прийти к тому же качественному выводу.

## 31. Приоритет 3 плана adversarial-robustness — probe на unanswerable/out-of-corpus вопросах (добавлено 2026-08-28)

**Контекст.** Единственный на момент раздела 30 полностью непротестированный класс поведения пайплайна: правильно ли он отказывается отвечать (`FINAL ANSWER: INSUFFICIENT_CONTEXT`, конвенция самого пайплайна — см. раздел 7 и `pipeline/generation.py`), когда в проиндексированном корпусе объективно нет данных для ответа, или вместо этого генерирует правдоподобное, но необоснованное число. Собственный раздел «Известные ограничения» проекта (README) до этого момента вообще не упоминал этот риск — не потому, что он был сознательно взвешен и отложен (как, например, Приоритет 5 выше), а потому, что не был протестирован никогда. Мотивация Приоритета 3 из `claude/plan_adversarial_robustness_priorities.md`: «Дёшево тестируется: сконструировать вопросы про периоды/темы, отсутствующие в корпусе, и проверить, отказывается ли система отвечать или генерирует правдоподобное, но необоснованное число».

**Метод.** 32 вопроса, две группы, обе программно проверены против реальных данных корпуса (`data/unanswerable_probe/build_questions.py::verify_absence()`), не предположены:

- **`wrong_year` (20 вопросов)** — компания реально есть в корпусе, но вопрос про финансовый год, которого для неё в корпусе нет. Проверено по годам, встроенным в `file_name` (FinQA/ConvFinQA), и по `report_year` (TAT-DQA, где буквально все строки — 2019 год, поэтому любой другой год гарантированно отсутствует).
- **`absent_company` (12 вопросов)** — реальная, хорошо известная публичная компания, полностью отсутствующая в корпусе. Проверено не только по колонке `company_name` (метаданные), но и полнотекстовым поиском по всем индексируемым полям (`pre_text`/`post_text`/`table`/`context`) — первый вариант списка (Alphabet, Meta, Tesla, Nvidia, Home Depot, Coca-Cola) был отбракован именно на этом шаге: эти компании отсутствовали в `company_name`, но реально упоминались в тексте как peer-group/конкуренты других компаний (например, Meta — 220 раз, Home Depot — 580 раз), то есть retrieval теоретически мог их найти. Финальный список (Amazon, Netflix, Berkshire Hathaway, Costco, UnitedHealth Group, ExxonMobil, Airbnb, Spotify, Salesforce, ServiceNow, Snowflake, DoorDash) подтверждён нулевым числом упоминаний где бы то ни было в индексируемом тексте.

Прогон — `notebooks/run_unanswerable_probe.py`, реальный платный прогон (retrieval → rerank → generation, без judge-вызова — сверять не с чем, у этих вопросов по определению нет gold-ответа; ~$0.015/вопрос, ниже обычного ~$0.016/вопрос из раздела 15 ровно на стоимость пропущенного judge-вызова). Результаты пишутся сразу на Google Drive построчно по ходу прогона (не локально с копированием в конце — раздел 1 п.3, тот же паттерн, что и в `reevaluate_phase6_adaptive.py`), с resume по `probe_id`. Классификация ответа программная, по тому же маркеру `FINAL ANSWER:`, который использует остальной пайплайн: `answer_text == "INSUFFICIENT_CONTEXT"` → `refused`, иначе → `confident_answer`. Полный `raw_response` (не только извлечённый маркер) сохранён для каждого вопроса — без него нельзя отличить настоящую уверенную выдумку от отказа прозой, не попавшего в точный формат маркера (уже наблюдавшийся класс ошибки, см. `pipeline/generation.py`).

**Результат.** 32/32 = 0 `confident_answer`, 0 случаев пустого retrieval-пула (`n_reranked` — всегда 5, то есть каждый вопрос дошёл до генерации; отказ — решение модели на этапе генерации, а не тривиальный случай «нечего было передать»). Несколько примеров `raw_response`, где модель прозой явно называет причину несовпадения, а не просто выдаёт маркер:

- ExxonMobil: «The provided documents contain data about Marathon Oil and Schlumberger, not ExxonMobil... FINAL ANSWER: INSUFFICIENT_CONTEXT»
- Netflix: «the provided documents contain information about News Corp and Discovery, Inc., but no information about Netflix's streaming revenue... FINAL ANSWER: INSUFFICIENT_CONTEXT»
- Walmart (wrong_year): «The provided context only contains Walmart's fiscal 2018 (and prior years) data... There is no data for fiscal year 2023... FINAL ANSWER: INSUFFICIENT_CONTEXT»

Cohere rerank-скор топ-кандидата (`top_rerank_score`) заметно выше для `wrong_year` (медиана ≈0.6–0.7, разброс ≈0.34–0.81) чем для `absent_company` (медиана ≈0.28–0.30, разброс ≈0.14–0.36) — согласуется с ожиданием: когда та же компания реально есть в корпусе (просто не за тот год), reranker находит генуинно более релевантный документ, чем когда компании нет вовсе. Это корреляционное подтверждение того, что retrieval вело себя осмысленно, а не доказательство того, почему именно отказалась модель — сама модель rerank-скор не видит. Сырой гибридный retrieval-скор (`top_retrieval_score`, RRF) в обеих группах сжат в узкий диапазон ≈0.008–0.016 — это масштаб самого RRF (сумма обратных рангов), а не сигнал о релевантности; не интерпретируется как «около шумового порога».

Сравнение с базовой частотой отказа на отвечаемых вопросах того же промпт-варианта (`config.generation.prompt_variant` по умолчанию — `"baseline"`, без переопределения в `config/config.yaml`; тот же вариант использован в `results/baseline_phase6/`, подтверждено `run_config.json`): на 250 отвечаемых вопросах `baseline_phase6` модель отказалась (`INSUFFICIENT_CONTEXT`) 7/250 = 2.8% раз. Прогоны `cite_and_check_phase6` (11/250) и `formula_base_phase6` (10/250) сюда не годятся как сравнение — это другие промпт-варианты (раздел 28), не тот же самый, что в probe. Итог: тот же промпт-шаблон отказывается отвечать ≈2.8% раз, когда ответ реально есть в контексте, и 100% раз (0/32), когда его там объективно нет — это не поведение модели, которая отказывается «на всякий случай» при любой неуверенности (промпт-инструкция также прямо запрещает отказ из-за второстепенного несовпадения деталей — см. раздел 7).

**Оговорки (честно, не для украшения).**

1. **n=32 — это не «пайплайн надёжно отказывается», это «в этой выборке отказ не редкий сбой».** 0 отказов из 32 даёт 95%-верхнюю границу (Клоппер–Пирсон) на истинную частоту фабрикации ≈9% в пуле; отдельно для `absent_company` (n=12, более рыхлая группа) верхняя граница шире, ≈22%. Пилот исключает частый сбой на этом типе вопросов, не редкий.
2. **`n_reranked` всегда 5 — это устройство retrieval (`pool_size`/`top_n` без порога релевантности), не признак «системе было трудно».** Ретривер по конструкции всегда возвращает полный пул, независимо от того, релевантен ли он вопросу. Это исключает только тривиальный вырожденный случай «пустой пул → автоматический отказ», не более.
3. **Протестирован только «лёгкий» вариант задачи.** Все 20 `wrong_year` вопросов — про метрику (выручка/чистая прибыль/маржа), которая уже широко представлена в корпусе для этой же компании, просто не за тот год. Не протестировано: отсутствие конкретной строки/метрики внутри реально проиндексированного отчёта той же компании и того же года (более тонкий случай, чем несовпадение года); компании с похожими на реальные названиями (коллизия тикера/дочерней структуры); компании, менее известные, чем протестированные — большинство из 12 `absent_company` — крупные, широко известные бренды, почти наверняка присутствующие в претрейн-знаниях самой модели. Отказ мог частично опираться на параметрическое знание модели («это Amazon, а не Marathon Oil»), а не только на честное «в контексте этого нет» — это другое утверждение, и оно не проверено отдельно.
4. **Итоговая формулировка находки:** на этом пилоте (n=32: 20 wrong_year + 12 absent_company) 0 из 32 вопросов привели к фабрикации числа (95%-ДИ на истинную частоту ≈0–9% по пулу, шире для подвыборки `absent_company` в одиночку — ≈0–22%); обоснование отказа в `raw_response` в части случаев явно называет причину несовпадения, retrieval/rerank-скоры разделяют две группы ожидаемым образом. Это исключает частую фабрикацию на данном типе вопросов, но не устанавливает устойчивость к более тонким вариантам (отсутствие метрики внутри присутствующего отчёта, компании с похожими названиями, компании вне претрейн-знаний модели) — они не протестированы.

**Материалы:** `data/unanswerable_probe/build_questions.py` (построение и верификация вопросов), `data/unanswerable_probe/questions.jsonl` (32 вопроса), `notebooks/run_unanswerable_probe.py` (прогон), `results/unanswerable_probe/probe_results.jsonl` (32 полных результата, включая `raw_response`).

**Статус:** закрыт в объёме этого пилота. Независимая критика интерпретации проведена (см. историю сессии) — три пункта из четырёх подтвердили вывод как обоснованный при условии оговорок выше; пункт про сравнение с базовой частотой отказа скорректирован (сравнение сузено с четырёх прогонов до одного — `baseline_phase6` — единственного с тем же промпт-вариантом).

## 32. Приоритет 2 плана adversarial-robustness — финансовые hard negatives, естественная и принудительная нагрузка на retrieval/reranker (добавлено 2026-08-29)

**Контекст.** Текущий Recall@5 = 0.944 измерен на чистом бенчмарке — вопросы задаются про конкретную компанию/год, остальной корпус для retrieval-стадии выступает фоном, а не намеренными обманками. Реальный клиентский корпус почти всегда содержит по-настоящему похожие документы: отчёты той же компании за другой год, отчёты компаний той же отрасли. До этого раздела вопрос «путает ли пайплайн их между собой» не имел числового ответа — только качественная оценка («явных признаков систематической ошибки reranker'а не обнаружено», раздел 21). Мотивация — `claude/plan_adversarial_robustness_priorities.md`, Приоритет 2; план эксперимента и его пересмотр по итогам самопроверки — `claude/plan_prioritet2_hard_negatives.md`.

Состоит из двух тестов: Тест 1 (бесплатный, ретроспективный — переиспользует уже оплаченный прогон) и Тест 2 (платный, ~$1.43, принудительный парный rerank-тест, прямая методологическая параллель с FinRank, arXiv:2608.07400).

### Тест 1 — естественная нагрузка (бесплатно, без единого нового API-вызова)

**Метод.** `scripts/analyze_hard_negative_stress.py`. Переиспользует `results/retrieval_trace_250/retrieval_trace.jsonl` (уже закоммиченный `candidate_top50`/`reranked_top5` для всех 250 вопросов, раздел 21) и `pipeline.ingestion.ingest()` (локальные метаданные из parquet, тоже бесплатно). Для каждого вопроса детерминированно (правило зафиксировано до просмотра результатов) выбирается hard-negative «сосед» в трёх категориях:

- **A** — тот же эмитент (`company_name`), другой `report_year` (ближайший по модулю год, при равенстве — лексикографически меньший `context_id`).
- **B** — тот же эмитент **и** тот же год, другой документ/раздел (лексикографически меньший `context_id` среди прочих в той же группе).
- **C** — тот же `company_sector`, другой эмитент (лексикографически меньший `context_id`; документы с пустым `company_sector` — 420/7318 — исключены только из этой категории).

Для каждого найденного соседа проверяется, попал ли он в сохранённый `candidate_top50` и/или в `reranked_top5`, и если да — на каком ранге относительно gold-документа.

**Один найденный и исправленный баг.** `report_year` хранится строкой (`'2009'`, не `2009`); скрипт первой версии падал на `abs(str - str)` в категории A — исправлено явным `int()`, безопасность каста проверена по всему корпусу (21 уникальный год, 1999–2019, все значения — чистые числовые строки) перед применением.

**Проверка корректности.** Пересчитанный overall Recall@5 = 241/250 (96.4%) точно совпадает с уже задокументированной в разделе 21 таблицей attribution: `success` (186) + `generation_failure_candidate` (55) = 241 — ровно те вопросы, где gold-документ пережил rerank и дошёл до финального топ-5. Совпадение с числом, посчитанным независимо двумя днями раньше другим кодом (`pipeline/attribution.py`) — сильное свидетельство корректности сопоставления `question_id`↔`trace`↔`rank`, не совпадение подгонки.

**Находка 1 (методологическая).** Деление на «stress» и «non-stress» подвыборки внутри прогона не работает как задумано: у 250 из 250 вопросов нашёлся хотя бы один сосед (в основном за счёт категорий B — 246/250 и C — 199/250), non-stress подвыборка пуста (n=0). Не баг скрипта, а свойство корпуса: 309 эмитентов сгруппированы всего в 68 секторов, поэтому «тот же сектор, другой эмитент» почти всегда находится. Зафиксировано как честный пересмотр метода, а не скрыто.

**Находка 2 (по категориям).**

| Категория | Вопросов с соседом | Сосед уже в top50 | Сосед в финальном top5 | Сосед обгоняет gold в top50 | Сосед обгоняет gold в top5 | Сосед вытеснил gold из top5 |
|---|---|---|---|---|---|---|
| A (тот же эмитент, др. год) | 126 | 60 (47.6%) | 17 (13.5%) | 5 | 1 | 0 |
| B (тот же эмитент+год, др. документ) | 246 | 179 (72.8%) | 57 (23.2%) | 11 | 11 (4.5%) | 1 |
| C (тот же сектор, др. эмитент) | 199 | 4 (2.0%) | 0 | 0 | 0 | 0 |

Категория C практически не создаёт естественной нагрузки на retrieval (4/199 даже в пуле топ-50) — обнадёживающе на этой стадии, но не то же самое, что нулевая уязвимость при принудительном сравнении (см. Тест 2). Категория B — самая содержательная, буквально «почти-дубликат» с точки зрения BM25/эмбеддинга: 11 из 246 (4.5%) случаев, где сосед обгоняет gold уже в финальном топ-5, и 1 случай, где сосед вытеснил gold из топ-5 целиком.

**Находка 3 (конкретный кейс).** Тот единственный случай категории B, где сосед вытеснил gold из top5 (`tatqa_train_8524`), — один из 7 вопросов, задокументированных в разделе 10 как «явный отказ (`INSUFFICIENT_CONTEXT`) при существующем gold-ответе». До этого теста причина отказа не была известна. Теперь известна: gold-документ был найден на 1-м месте пула топ-50 до rerank'а, но после rerank'а документ того же эмитента за тот же год занял 3-е место в финальном топ-5, а gold выпал из топ-5 полностью — модель не видела нужный чанк, отсюда честный отказ, а не выдумка. Проверка по всем 9 задокументированным (раздел 21) случаям `reranking_failure`/`retrieval_failure`: только 2 из 9 объясняются hard-negative-соседями этого теста (`tatqa_train_8524` — чисто; `convfinqa_3418` — частично). Остальные 7 из 9 не объясняются этим узким определением — hard negatives не главная причина retrieval-ошибок пайплайна, лишь один подтверждённый механизм из нескольких.

### Тест 2 — принудительный парный rerank-тест (платно, ~$1.43, 571 реальных вызовов Cohere Rerank v4.0 Pro)

**Метод.** `scripts/run_hard_negative_pairwise_test2.py`, реальный платный прогон в Colab. Для каждой из 571 пар (126 категория A, 246 B, 199 C — те же детерминированные пары, что и в Тесте 1, без пересчёта) — изолированный вызов `rerank()` с ровно двумя кандидатами (gold + сосед), `top_n=2`, ничего больше в списке. Полный объём (все 571 пар, все 3 категории), а не только «непокрытые Тестом 1» пары — итоговое решение, пересмотренное дважды в процессе подготовки (см. «Что изменилось» ниже).

**Полный `full_indexed_content` документа-соседа** (`metadata_prefix + contextual_summary + raw_content`) берётся напрямую из уже проиндексированной MongoDB-коллекции по `context_id` (бесплатно, без нового LLM-вызова, всегда точная копия того, что реально в индексе), с проверкой целостности по `content_sha256` там, где он уже зафиксирован в `retrieval_trace_250`.

**Соблюдение обязательного правила сохранения платных прогонов** (раздел 1 правил репозитория, раздел 11 ТЗ, раздел 29): каждая пара пишется сразу на примонтированный Google Drive по ходу прогона через `find_canonical_root(...)/hard_negative_pairwise_test2/pairwise_results.jsonl` — не в локальный `results/` с копированием в конце. Чекпоинт/resume по `(question_id, category)`. `verify_run_files()` в конце подтверждает полноту уже долговечного вывода, не создаёт его.

**Проверка корректности.** Сводка независимо пересчитана из сырого `pairwise_results.jsonl` (571 строка) — совпала с тем, что напечатал скрипт в Colab, до последней цифры. Дополнительно: 571 уникальная пара `(question_id, category)`, дублей нет; `content_integrity_verified` — 0 расхождений по всем 571 парам (корпус не дрейфовал с 21 августа); ничьих — 0; пропущенных результатов — 0.

**Главный результат — pairwise accuracy по категориям:**

| Категория | Пар | Побед gold | Accuracy | 95% ДИ (Wilson) |
|---|---|---|---|---|
| A (тот же эмитент, др. год) | 126 | 125 | 99.2% | [95.6%, 99.9%] |
| B (тот же эмитент+год, др. документ) | 246 | 234 | 95.1% | [91.7%, 97.2%] |
| C (тот же сектор, др. эмитент) | 199 | 199 | 100.0% | [98.1%, 100%] |

**Находка 1 — из 13 «проигрышей» решающий только один, остальные 12 неотличимы от шума измерения.** Разница relevance-скора gold и соседа в проигрышных случаях: в категории B (12 проигрышей) у 11 из 12 разница — от 0.0002 до 0.0084 (медианная выигрышная разница в этой же категории — 0.24, на два порядка больше); единственный проигрыш категории A (`convfinqa_969`) — тоже крошечная разница, 0.0039. Единственное решительное расхождение (margin 0.0481, в ~6 раз больше следующего по величине проигрыша) — `tatqa_train_8524`, категория B. У этого пайплайна практически нет случаев, где reranker уверенно предпочёл неверный документ; 12 из 13 формальных «проигрышей» неотличимы от шума измерения, 1 — настоящий, воспроизводимый сбой.

**Находка 2 — единственный решительный сбой независимо подтверждён вторым методом измерения.** `tatqa_train_8524` — тот же вопрос, который Тест 1 определил как причину одного из 7 задокументированных «честных отказов» (раздел 10). Изолированный принудительный вызов, отдельно от остального пула, воспроизводит тот же результат: сосед получает более высокий relevance-скор (0.7503 против 0.7022 у gold). Два разных метода измерения (естественный 50-документный батч и изолированная пара) сошлись в одном и том же выводе для одного и того же случая.

**Находка 3 (не доказана, только совпадение).** Единственный проигрыш категории A — `convfinqa_969` — тот же вопрос, что ранее (раздел 25, Фаза 3 разбора generation-ошибок) был отнесён к категории `question_label_mismatch`: вопрос сформулирован как «operating profits», а gold-программа на самом деле считает «operating revenues» — статью, которая в тексте вообще не упоминается под таким названием. Правдоподобно, что несовпадение формулировки вопроса с содержанием gold-документа могло повлиять на relevance-скор, но margin (0.0039) на том же уровне шума, что и остальные 11 «мягких» проигрышей категории B — зафиксировано как корреляция, не причинно-следственная связь.

**Проверка допущения о независимости скоринга — подтверждена.** Дизайн Теста 2 опирается на допущение, что Cohere Rerank v4.0 Pro скорит пару «запрос-документ» независимо от остального батча (обычное поведение cross-encoder reranker'ов, но официально Cohere это не подтверждает). Скрипт сверил результат принудительного парного вызова с уже известным естественным порядком (из Теста 1) везде, где этот порядок был независимо определим — 242 сопоставимых случая. Совпадение — 242 из 242 (100%, 95% ДИ [98.4%, 100%]).

**Сравнение с FinRank — честная оговорка, не прямое сопоставление.** У FinRank сравниваемая величина — падение pairwise accuracy (13.0–20.5 п.п., random→curated hard negatives). Этот тест не измерял accuracy на случайных негативах для данного пайплайна — только на курируемых hard negatives. Прямо вычислить свою «дельту» и сопоставить её с диапазоном FinRank нельзя без такого же базового прогона на случайных негативах, которого здесь не было. Что можно сказать честно: абсолютная accuracy на курируемых hard negatives (95.1–100%) высокая сама по себе, вне зависимости от того, с какого уровня она бы «упала» относительно случайных негативов.

### Что изменилось в дизайне по сравнению с первой версией плана

Первая версия `claude/plan_prioritet2_hard_negatives.md` предлагала тестировать в Тесте 2 только «непокрытые Тестом 1» пары (сосед не попал в естественный `candidate_top50`) и рекомендовала пропустить категорию C. При подготовке скрипта и самопроверке (по прямому вопросу «всё ли учтено, какой объём выбрать правильно») обе позиции пересмотрены до платного прогона:

1. Определение «уже покрыто Тестом 1» было чуть шире, чем корректно: если сосед попал в top50, но и gold, и сосед оба не попали в финальный top5, их относительный порядок всё равно неизвестен (`retrieval_trace.jsonl` хранит только топ-5 после rerank'а, не полный ранжированный список 50 кандидатов). На реальных данных расхождение — 1 пара из 571 (несущественно на практике), но рассуждение было неверным в принципе.
2. Категория C изначально рекомендовалась к пропуску (нулевая естественная нагрузка в Тесте 1), но именно C — доминирующая категория у FinRank (79.8% их hard negatives). Пропуск терял бы сопоставимость именно там, где она нужнее всего, при тривиальной разнице в стоимости ($1.43 против $0.28) — рекомендация пересмотрена на полный объём, все 571 пар, до запуска платного прогона.

### Оговорки (честно, не для украшения)

1. **Пары, не пропорции корпуса.** 571 пара — это все детерминированно найденные соседи для 250 вопросов ошибки attribution-прогона, не случайная выборка по всему корпусу из 7318 документов; категория B/C систематически перепредставлены относительно A просто потому, что у большинства эмитентов больше документов-соседей в своей группе компания+год или секторе, чем других годовых отчётов.
2. **Один воспроизводимый сбой на выборке этого размера не даёт надёжной оценки истинной частоты.** 1 решительный проигрыш из 246 пар категории B — точечная оценка 0.4%, но 95%-ДИ на accuracy (91.7–97.2%) достаточно широк, чтобы не заявлять точную частоту сбоя ниже этого диапазона.
3. **Дельта-сравнение с FinRank не измерено**, как указано выше — нет базового прогона на случайных негативах для этого пайплайна; сопоставляется только абсолютная accuracy на курируемых hard negatives, не падение относительно случайных.
4. **Детерминированный выбор одного соседа на категорию, не всех возможных.** Например, категория A берёт ближайший по году отчёт того же эмитента, а не все другие годы; если у эмитента есть более отдалённый по году, но более похожий по содержанию отчёт, он не протестирован.
5. **`convfinqa_969` (Находка 3) — корреляция, не причина**, как явно отмечено выше.
