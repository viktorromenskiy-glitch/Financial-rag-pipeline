## 1. Датасет и корпус

- **Источник:** T²-RAGBench = FinQA + ConvFinQA + TAT-DQA, объединены по методологии готового прецедента ([huggingface.co/datasets/G4KMU/t2-ragbench](https://huggingface.co/datasets/G4KMU/t2-ragbench), [paper](https://www.inf.uni-hamburg.de/en/inst/ab/lt/publications/2026-strich-t2ragbench.pdf)).
- **Масштаб:** 7318 документов (текст+таблица), 23088 вопросов.
- **Почему этот датасет:** признанный сложный тестовый случай для RAG — точные числовые ответы, высокая цена ошибки, смешанный текст+таблица формат. Обоснование ниши для портфолио — сложность датасета, не отраслевая статистика Upwork (см. `itogovyi_vyvod_proekt.md`).

## 2. Хранилище

- **MongoDB Atlas, тариф M0** (бесплатный, лимит 512 МБ и 3 search-индекса на инстанс — учитывать при создании новых коллекций для тестов).
- **Коллекция:** `rag_project.t2_ragbench_full`.
- **Имена индексов (константа, не хардкодить в разных местах кода):**
  - `vector_index_full` — векторный индекс, поле `embedding_voyage`
  - `text_index_full` — полнотекстовый индекс, поле `full_indexed_content` (исправлено 2026-08-09 — по итогам ревью, старое значение `context` было устаревшим: это имя поля из ранней версии схемы модуля 1/Ingestion, финальная схема индексации — модуль 5, поле `full_indexed_content`)

  Несовпадение этих имён с чем-либо ещё в коде уже один раз вызвало тихий баг: `$vectorSearch`/`$search` в MongoDB не бросает ошибку на несуществующее имя индекса, просто возвращает пустой результат — из-за этого баг легко спутать с "reranker всё сломал". Имена должны быть в конфиге, проверяться при старте пайплайна (явный assert на непустой результат тестового запроса), не потеряться повторно.

- **Риск лимита в 3 search-индекса на инстанс M0 (замечание внешнего ревью, подтверждено дважды в собственной истории проекта — `poshagovyi_plan_vypolneniya.md`, тест 1.3: тестовую коллекцию пришлось удалить, чтобы освободить слот; тест 2.3: сознательно выбран локальный RRF вместо Atlas именно чтобы не упереться в этот лимит повторно):** основная коллекция уже занимает 2 из 3 слотов (`vector_index_full` + `text_index_full`), свободен **только один**. В неделе 4 любое дополнительное тестирование, требующее отдельного индекса (например, сравнение embedding-моделей на полном корпусе, а не только на подвыборке n=50-80 из п.3) рискует упереться в лимит снова. **Решить заранее, до недели 4, не постфактум:** апгрейд тарифа Atlas (платный, снимает лимит) или отдельный временный кластер для экспериментов, не трогающий основную коллекцию `t2_ragbench_full`.

## 3a. Пересмотр embedding-модели: per-dataset routing (добавлено 2026-08-15)

По итогам ревью трёх независимых ИИ (Gemini, Kimi, Grok — консультация про рычаги повышения точности, `promt_dlya_grok_svod_gipotez.md` и последующие уточнения) все три сошлись на рекомендации перейти на `voyage-finance-2` (доменный финансовый embedding) вместо `voyage-4` (general-purpose), опираясь на официальный бенчмарк Voyage AI (NDCG@10: FinQA 0.795, ConvFinQA 0.820, TAT-QA 0.788, среднее 0.831 по 11 датасетам — `blog.voyageai.com/2024/06/03/domain-specific-embeddings-finance-edition-voyage-finance-2/`). Экстраполяция экспертов на end-to-end эффект (+3-8 п.п.) была прямо помечена ими как неподтверждённая оценка, не измеренный факт — решено не принимать на веру и измерить прямым A/B на собственном корпусе, а не на бенчмарке производителя.

**Метод.** Retrieval-only A/B (без generation/judge — чистое сравнение Recall@5 между `voyage-4` и `voyage-finance-2` на одном и том же индексированном пуле документов). Три последовательных прогона возрастающего масштаба:

| Прогон | Источник вопросов | n на датасет | n всего |
|---|---|---|---|
| 1 | `eval_subset_250.parquet` (курированный eval-набор) | 29 (ConvFinQA) / 90 (FinQA) / 97 (TAT-DQA) | 200 |
| 2 | Полный набор T²-RAGBench (`pipeline.ingestion`, стратифицированная выборка) | 700 | 2100 |
| 3 | Полный набор T²-RAGBench | 2500 | 7500 |

Значимость — McNemar's exact test (`scipy.stats.binomtest` на дискордантных парах) — тот же метод, которым в проекте уже валидировался `metadata_prefix` (п.4, McNemar p=0.00195).

**Итоговый результат (прогон 3, n=2500 на датасет, финальный, полный корпус 7318 документов):**

| source_dataset | Recall@5 voyage-4 | Recall@5 voyage-finance-2 | Δ | McNemar exact p |
|---|---|---|---|---|
| ConvFinQA | 0.971 | 0.952 | −0.019 | **0.0000** |
| FinQA | 0.968 | 0.959 | −0.009 | 0.0214 |
| TAT-DQA | 0.902 | 0.921 | +0.019 | **0.0005** |
| Overall | 0.947 | 0.944 | −0.003 | 0.2429 (не значимо) |

Направление эффекта воспроизвелось стабильно во всех трёх прогонах (ConvFinQA хуже, TAT-DQA лучше, FinQA нейтрально/слегка хуже) — не случайный выброс одного измерения. Overall-агрегат не значим, потому что разнонаправленные эффекты по датасетам взаимно гасятся при усреднении — прямое подтверждение того, что решение должно приниматься по `source_dataset` (см. уже действующее требование п.10 «Стратификация метрик»), не одной сводной цифрой.

Это прямо расходится с прогнозом всех трёх консультантов (равномерный прирост по всем источникам) — реальный эффект неравномерный и по двум из трёх источников отрицательный или нейтральный.

**Вопрос множественных сравнений.** Три независимых ИИ разошлись во мнениях: Gemini настаивала на обязательности Bonferroni-поправки через closed testing (Marcus, Peritz & Gabriel, *Biometrika*, 1976; Westfall & Young, 1993) — цитаты подтверждены, но применимость к нашему случаю (не пре-регистрированная иерархическая gatekeeping-процедура) оспорена при собственной проверке. Grok и Kimi — со ссылкой на Rothman (*Epidemiology*, 1990), Saville (*The American Statistician*, 1990) и Bender & Lange (*J Clin Epidemiol*, 2001, тот же источник, что уже используется в п.9 этого ТЗ) — считают, что одна заранее сформулированная гипотеза (TAT-DQA выигрывает — сформулирована до измерения, на основании анализа ошибок Zhu et al., ACL 2021, Table 6/§4.3, Wrong Evidence 55% + Missing Evidence 29%) не требует поправки по семейству из формально не связанных тестов. **Проект уже имеет собственную политику по этому вопросу (см. п.9: «поправка на множественные сравнения не применяется... каждый тест отвечает на отдельный вопрос с отдельной нулевой гипотезой»)** — по этому стандарту корректировать не нужно ни при каком n. Вопрос стал практически неактуален после прогона 3: TAT-DQA (p=0.0005) уверенно проходит даже строгий Bonferroni-порог (0.05/4=0.0125), FinQA (p=0.0214) — нет, но эффект там мал (−0.9 п.п.) и не меняет решения.

**Решение: per-dataset embedding routing.** `voyage-finance-2` — для документов и запросов TAT-DQA. `voyage-4` — для ConvFinQA и FinQA (везде либо явный регресс, либо отсутствие выигрыша от смены модели).

**Известное ограничение, не решённое этим ТЗ (зафиксировать честно, не маскировать под готовое решение):** на этапе индексации `source_dataset` документа известен всегда (поле есть в `DocumentRecord`, модуль 1) — выбор embedding-модели для документа однозначен. На этапе запроса, при `eval`, `source_dataset` тоже известен из метаданных вопроса — но в гипотетической «живой» системе без размеченного входящего запроса эта метка не была бы доступна заранее, и выбор модели для кодирования запроса потребовал бы отдельного классификатора запроса или dual-embed с последующим слиянием результатов — не реализовано и не тестировалось. Для масштаба этого портфолио-проекта (eval на T²-RAGBench, где `source_dataset` всегда известен) это ограничение не блокирует внедрение, но должно быть явно отмечено в README (раздел Known limitations) как нерешённый вопрос при гипотетическом переходе к продакшену с неразмеченным трафиком.

## 4. Retrieval

- **Метод:** hybrid `$rankFusion` (BM25 полнотекстовый + dense векторный), веса 0.5/0.5 — **не подобраны локальным тюнингом, взяты как разумный дефолт** (замечание внешнего ревью: формулировка важна — это не «проверенный оптимум», а сознательно не потраченное на тюнинг время; если в неделе 4 будет запас, недорогой grid search на eval-подвыборке может дать дополнительный прирост, но не блокирует текущую готовность).
- **Размер пула кандидатов:** top-50 (обоснование в п.6).
- **Baseline Recall@5 (без reranker, без enrichment, полный корпус, n=250):** 0.808.

## 5. Contextual enrichment (этап индексации)

- **Метод:** Claude Haiku 4.5, короткая справка (1-2 предложения) на документ, prompt caching. Опциональный шаг, конфиг-флаг `enrichment.enabled`.
- **Стоимость на весь корпус:** ~$10 (экстраполяция с теста на 450 документах, $0.619 фактически, ×16.3).
- **Эффект (n=1535, hybrid retrieval, без reranker):** Recall@5 0.925 → 0.933, +0.78 п.п., **значимо** (p=0.0164, 95% CI [0.20%, 1.43%]).
- **Решение:** используется. Обогащение корпуса при индексации, не на этапе запроса.
- **Важно для реализации (снимает возможную неоднозначность):** обогащение меняет `context` документа **до** индексации и эмбеддинга. Дальше по пайплайну — и retrieval, и reranker — работают с уже единым текстом (обогащённым, если `enrichment.enabled=true`), а не с двумя параллельными версиями документа. Это не развилка на этапе исполнения запроса, а последовательность: enrichment → единый текст → retrieval → reranking. (Тест аддитивности на 150 вопросах, где raw и enriched сравнивались как отдельные ветки, был инструментом измерения эффекта, не описанием архитектуры финального пайплайна.)
- **Схема документа в MongoDB (уточнено по итогам ревью, 2026-08-09):** хранить `raw_content` (исходный текст) и `contextual_summary` (справка от Haiku) отдельными полями, не только объединённый результат — полезно для отладки и на случай изменения промпта обогащения без пересчёта retrieval с нуля. Поле, по которому реально идёт поиск/reranking/подаётся в generation — `full_indexed_content` = `contextual_summary + "\n\n" + raw_content` (или пустая строка вместо summary, если `enrichment.enabled=false`). Именно это (одно) поле и есть тот "единый текст" из пункта выше.
- **Открытый риск, не закрытый тестами (зафиксировать явно, не маскировать под уже проверенное):** Recall@5=0.944 (reranker, пул=50) измерен **на полном корпусе** 7318 документов (та же коллекция `t2_ragbench_full`, что и baseline 0.808) — это не экстраполяция с уменьшенной выборки. А вот совместный эффект reranker+enrichment (Recall@5=0.980 на подвыборке 150 вопросов) измерялся **на уменьшенном корпусе 450 документов** — не проверялся на полных 7318. Тот же уменьшенный корпус (450 документов) использовался и для самого эффекта enrichment без reranker'а (+0.78 п.п., n=1535, п. выше) — оба числа не подтверждены на полном масштабе, не только их комбинация. Финальный сквозной прогон (неделя 4) должен явно измерить Recall@5 с обоими механизмами включёнными на полном корпусе — до этого момента ни 0.980, ни +0.78 п.п. не считать подтверждёнными для README.
- **Взаимодействие enrichment и reranker (raw vs enriched ветки, не проверено попарно):** тест аддитивности на 150 вопросах сравнивал две ветки — Raw (0.953→0.993 после rerank, +4.0 п.п., p=0.0346) и Enriched (0.960→0.980, +2.0 п.п., p=0.3494) — каждую **отдельно со своим baseline до rerank**, не друг с другом напрямую. То, что у raw прирост значим, а у enriched нет, не означает, что ветки статистически отличаются между собой (классическая ошибка интерпретации — разница между «значимо» и «не значимо» сама по себе не обязательно значима, см. Gelman & Stern, *The American Statistician*, 2006). Более высокий старт enriched-ветки (0.960 vs 0.953) — правдоподобная альтернатива «эффекту потолка», не требующая гипотезы об «отравлении» reranker'а обогащённым текстом. Прямой paired-тест (raw+rerank vs enriched+rerank на одних и тех же вопросах) не проводился — недорого сделать по уже сохранённым результатам теста (без новых вызовов API) параллельно с началом кодирования; результат дописать сюда. Текущая архитектура (единое поле `full_indexed_content`, без раздельных `rerank_content`) остаётся рабочим дефолтом независимо от исхода этого пересчёта — заводить отдельное поле впрок не оправдано (переиндексация корпуса при необходимости — недорогая операция).

## 6. Reranker

- **Модель:** Cohere Rerank v4.0 Pro (production-ключ, не trial — лимит 1000 вызовов/мес на trial уже был исчерпан один раз).
- **Размер пула:** **50** — эмпирически оптимален, не просто выбран по прецеденту статьи:

  | Пул | Recall@5 (n=900, точный McNemar) | vs предыдущий |
  |---|---|---|
  | — (без reranker) | 0.8344 | — |
  | 10 | 0.8900 | +5.56 п.п. vs baseline, p<0.0001 |
  | 50 | 0.9444 | +5.44 п.п. vs пул=10, p<0.0001 |
  | 100 | 0.9411 | −0.33 п.п. vs пул=50, p=0.58 (не значимо) |

- **Обрезка текста документа перед reranking: ЗАПРЕЩЕНА.** Это критичный, дважды подтверждённый факт: обрезка до 2000 символов (93.2% целевых документов длиннее — медиана 4263 символа) превращала прирост reranker'а в регресс (Recall@5 падал до 0.608-0.764 вместо роста). После снятия обрезки тот же reranker дал устойчивый прирост. Полный текст документа должен передаваться в Cohere API без сокращения независимо от длины.
- **Финальный Recall@5 (пул=50, без обрезки, n=900):** 0.944.

## 7. Генерация ответа

- **Формат:** Direct (прямой текстовый ответ), не Program-of-Thought.
- **Модель:** Claude Sonnet 5.
- **Обоснование (развилка 9, тест 2.4):** на 30 gold-context вопросах PoT и Direct дали одинаковое число верных ответов (0.733 = 0.733) — разрыв, который PoT показывал на Codex в 2023 (Chen et al.), с современными моделями не воспроизвёлся на этой выборке. PoT требует безопасного исполнения кода без измеримого выигрыша — не оправдано. **Оговорка по формулировке (замечание внешнего ревью):** n=30 даёт низкую мощность — точное совпадение на этой выборке не означает доказанной идентичности методов в общем случае, только отсутствие обнаруженного на этих данных разрыва. Не переформулировать как «доказано, что PoT не даёт преимущества» — только «не обнаружено преимущества на измеренных данных».
- **Критично:** сравнение сгенерированного ответа с gold-ответом должно быть **инвариантно к знаку и масштабу** (доля 0-1 vs число 0-100 для процентов). Без этой инвариантности система оценки систематически занижает реальную точность модели — баг, найденный и исправленный в тесте 2.4/2.5 (`is_close_v2`).
- **Спецификация `is_close_v2` обязательна перед кодированием (пробел, найден внешним ревью):** ТЗ ссылается на эту функцию по имени, но её точная логика (допуск относительной/абсолютной погрешности, обработка `None`/нечисловых ответов, нормализация валютных символов и единиц измерения) нигде не задокументирована — перенести буквально из рабочего Colab-скрипта теста 2.4/2.5, не переписывать по памяти. Без этого число 0.733 невоспроизводимо другим человеком. Добавить юнит-тесты с конкретными примерами (`"100"` vs `"100.0"` vs `"1.00"` как доля, `"0.5"` vs `"50%"` и т.п.) — упрощает доверие к финальным метрикам для портфолио.
- **`temperature=0.0`** на всех вызовах генерации (и здесь, и в enrichment п.5, и в судье п.8) — без этого регрессионный анализ (п.10) будет давать шум от стохастичности модели, а не только от реальных изменений пайплайна. Это касалось и прошлых тестов недель 1-2 — параметр нигде явно не был зафиксирован, при реализации исправить.

## 8. LLM Judge Evaluation (переименовано из «RAGAS evaluation» по итогам ревью, 2026-08-09 — модуль не использует библиотеку RAGAS и её метрики faithfulness/answer relevancy/context precision, только кастомный judge + `is_close_v2`, старое название создавало ложные ожидания у портфолио-рецензента)

- **Модель:** Claude Sonnet 5, единственный судья.
- **Обоснование (развилка 7, тест 2.5):** 93.3% согласия (28/30) с детерминированной проверкой на 30 вопросах; оба расхождения — один и тот же объяснимый краевой случай (не сопоставление доли и процента), не хаотичный источник ошибок. Независимый второй judge (GPT-4o-mini) не нужен.
- **Кэширование результатов судьи:** ключ `hash(question + context + answer + judge_prompt_version)` — версия промпта судьи обязательно часть ключа, не только вопрос/контекст/ответ. Без неё смена промпта судьи (например, правка формулировки инвариантности к знаку/масштабу) тихо вернёт старые оценки, посчитанные по старому промпту, и будет неотличима от «ничего не изменилось» → сохранённый score. При повторных прогонах (например, менялась только генерация для части вопросов) — не пере-судить то, что не изменилось. Экономия API-бюджета при частых регрессионных прогонах (п.10 требует делать их после каждого значимого изменения).

## 9. Критерий «готово» (развилка 8)

- **Baseline-relative контроль**, не фиксированная абсолютная планка внешних метрик. Система считается готовой, когда финальные метрики значимо (paired bootstrap/McNemar, не просто численно) превосходят собственный baseline проекта на каждом значимом изменении пайплайна — не когда достигнуто произвольное внешнее число.
- **Поправка на множественные сравнения (Bonferroni/FDR) не применяется.** Все статистические сравнения в проекте — заранее спланированные проверки конкретных архитектурных развилок, проводятся последовательно: результат одного теста определяет следующий шаг (нужен ли reranker → какой pool_size → нужен ли enrichment и т.д.), не одновременная батарея гипотез на одних данных с выбором лучшей по минимальному p-value. Каждый тест отвечает на отдельный вопрос с отдельной нулевой гипотезой — не часть одного семейства для FWER-поправки. Финальное сравнение (baseline vs итоговый пайплайн) — единственный тест, поправка не требуется по определению. При публикации сводной таблицы конфигураций в финальном отчёте — явно указать в подписи, что конфигурации тестировались последовательно, а не выбирались post-hoc по минимальному p-value.

## 10. Обязательные этапы оценки (не опциональные, включать в каждый релевантный модуль)

- **Диагностика ошибок по типам** до внесения изменений — не гадать, какая техника нужна, а сначала посмотреть, где именно baseline ошибается (retrieval miss / неверная таблица / генерация ошиблась).
- **Регрессионный анализ после каждого значимого изменения** — не только агрегированная метрика, а сравнение по конкретным вопросам: что было верно и стало неверно, и наоборот. Несколько раз в этом проекте именно так находились реальные баги, скрытые за стабильной или даже улучшившейся общей метрикой (пример — bge-reranker: 13 исправлено, но 44 сломано, при том что метрика могла выглядеть нейтрально).
- **Финальный ручной разбор 10-20 оставшихся ошибок**, классификация по паттернам — не ради метрики, а ради понимания (прецедент из Text-to-SQL: 91% ошибок оказались логическими и концентрировались на одной схеме).
- **Стратификация метрик по `source_dataset`** (FinQA / ConvFinQA / TAT-DQA — поле уже есть в `DocumentRecord`, модуль 1) обязательна в финальном отчёте, не только агрегированный Recall@5/accuracy по всему корпусу. Датасеты качественно разные (одношаговые числовые вопросы vs многоходовый диалог vs таблице-тяжёлые документы) — агрегат может скрывать, что пайплайн уверенно работает на одном источнике и заметно хуже на другом. Дёшево (поле уже есть, просто группировка при отчёте), но даёт содержательно более честный и сильный результат для портфолио, чем одно число.

## 11. Устойчивость к сбоям API и дедупликация (добавлено по итогам финального ревью, 2026-08-09)

- **Retry с экспоненциальным backoff** на всех вызовах внешних API (Voyage, Claude, Cohere) — `tenacity`, `stop_after_attempt(5)`, `wait_random_exponential(min=1, max=60)`. Не изобретать вручную (как временные `time.sleep()` в тестовых скриптах недель 1-2) — там это было оправдано для быстрого теста, для продакшен-кода пайплайна использовать библиотеку. **Уточнение (замечание внешнего ревью):** ретраить только transient-ошибки (429 rate limit, 5xx, таймауты соединения) — не 4xx-ошибки вида 400 Bad Request, которые сигнализируют баг в самом запросе и ретраем не лечатся, только маскируют проблему повторными бесполезными вызовами.
- **`run_config.json` рядом с каждым сохранённым прогоном** (предложено дважды независимыми ревью) — snapshot конфигурации, породившей эти результаты: модель embedding, `enrichment.enabled`+модель+версия промпта, `reranker.enabled`+модель+`pool_size`, модель generation, `judge_prompt_version`. Без этого через несколько недель тестирования невозможно восстановить, какому именно прогону соответствует сохранённый набор ответов — критично для регрессионного анализа (п.10).
- **Checkpointing состояния при индексации всего корпуса** — прогресс (какие документы уже обогащены/проэмбеждены/проиндексированы) сохраняется во внешнее состояние (JSONL-файл или поле `is_indexed: true` прямо в MongoDB), не только в памяти рантайма. Тот же принцип, что уже применялся вручную во всех Colab-тестах (сохранение каждые 25-50 вопросов) — здесь формализуется как требование модулей 4 и 5, не разовый приём.
- **Без сложной асинхронности** (Celery/распределённые очереди) — не оправдано для масштаба проекта. `concurrent.futures.ThreadPoolExecutor` для батчевых вызовов API — достаточно.
- **Assert на отсутствие дубликатов** `context_id` в результатах `$rankFusion` (модуль 6) — Atlas обрабатывает это нативно, но проверка на уровне кода дешева и защищает от тихих ошибок при возможных изменениях в реализации.

## 12. Итоговая конфигурация пайплайна

```
Ingestion (FinQA+ConvFinQA+TAT-DQA)
  → Chunking (формат датасета, без отдельной сериализации таблиц)
  → Contextual enrichment (Claude Haiku 4.5, опционально по конфигу)
  → Embedding (Voyage-4, эмбеддится full_indexed_content — уже с учётом enrichment, если включён)
  → Indexing (MongoDB Atlas: vector_index_full + text_index_full)
  → Hybrid retrieval ($rankFusion, top-50)
  → Reranking (Cohere Rerank v4.0 Pro, пул=50, полный текст, top-5)
  → Generation (Direct, Claude Sonnet 5, знак/масштаб-инвариантный формат)
  → LLM Judge Evaluation (Claude Sonnet 5 judge + детерминированная кросс-проверка)
```

**Итоговый Recall@5 (retrieval-часть, n=900, полный корпус): 0.944.**

Все компоненты (reranker, enrichment, judge, embedding, pool_size) должны быть переключаемы через конфиг, не хардкод — см. `3.3 Структура репозитория`.
